## 0. 先建立三句话的全局观

在进入细节前，先把整个项目的「骨架」压缩成三句话：

1. **用例层不碰 driver，页面层不写等待，基础层不含业务。**
   - 用例只说「我要登录、我要加购、我要断言」；
   - 页面层只说「登录要填哪三个元素、加购按钮怎么按 slug 拼出来」；
   - 基础层只说「怎么等、怎么点、怎么输入、失败了怎么截图」。

2. **数据只有两个大来源：外部静态数据（YAML / 命令行 / 环境变量）和上一步的返回值。**
   - 静态数据决定「测什么、用哪个账号、期望值是多少」；
   - 返回值决定「下一步拿什么继续做」，例如商品 id → slug → 定位器 → 点击 → 角标文本。

3. **参数不是「把值填进函数」，而是「层与层之间的契约」。**
   - 入参决定这一层需要外部提供什么；
   - 出参决定这一层向上层交付什么；
   - 契约设计得好，上层不需要知道下层怎么实现；契约设计得差，参数就会到处乱飞。

## 1. 项目整体认知

### 1.1 一句话定位

这是一个面向 **Web 商城** 的 UI 自动化测试框架，被测系统是 Sauce Labs 官方的公开演示站 **Swag Labs（saucedemo）**，覆盖登录、商品列表、商品详情、购物车、结算下单、侧边栏菜单、页面通用场景、特殊账号异常行为共 8 个模块。

### 1.2 业务目标

用真实浏览器把用户的**核心购买链路**跑一遍，并在关键节点做数据一致性断言：

```
打开登录页
  → 输入账号密码登录
  → 进入商品列表
  → 查看商品 / 排序 / 加购
  → 进入商品详情
  → 进入购物车核对
  → 填写结算信息
  → 核对金额
  → 完成订单
  → 退出登录
```

框架不仅要「能跑通」，还要解决工程化问题：

- 用例怎么组织、怎么复用前置步骤；
- 测试数据怎么外置、怎么参数化；
- 失败时怎么留下现场（截图、录屏、控制台日志、页面源码）；
- 结果怎么进报告、怎么在 CI 里跑。

### 1.3 技术栈

| 组件 | 版本（项目锁定） | 在本项目中的角色 |
| --- | --- | --- |
| Python | 3.10+ | 开发语言 |
| Selenium | 4.25.0 | 浏览器自动化原语（WebDriver） |
| Pytest | 8.3.4 | 用例收集、fixture、参数化、标记、钩子 |
| pytest-rerunfailures | 14.0 | 失败重跑（线上监控吸收站点抖动） |
| allure-pytest | 2.13.5 | 报告数据写入（步骤、附件、严重级别） |
| PyYAML | 6.0.3 | YAML 数据驱动 |
| Pillow | 11.1.0 | 失败录屏 GIF 合成 |
| ruff | 0.17.0 | 静态检查 |
| GitHub Actions | - | CI 定时任务 + GitHub Pages 报告 |

### 1.4 为什么是 Selenium 4，而不是 Playwright（面试常问）

一句话：**岗位方向 + 展示框架搭建能力 + 生态成熟度**。

- Selenium 只给 WebDriver 原语，等待策略、BasePage、失败治理、数据驱动、报告都要自己搭，正好展示「从 0 到 1」的工程能力；
- Playwright 自带自动等待、录屏、编排，很多框架层的活不用自己做；
- Selenium 是 W3C WebDriver 标准实现，Selenium Manager 自动管理驱动；
- 团队常见组合是 Selenium + Pytest，面试官能逐行追问。

> 反向追问「自动等待不是更先进吗？」：
> 自动等待把等待语义藏在框架内部，超时不可控、失败堆栈不指向业务；
> 本项目每次等待都对应明确的业务语义（等按钮可点击 / 等 URL 跳转 / 等文本变化），超时中文报错 + 截图 + 录屏，定位更快。

## 2. 五层架构：每一层到底负责什么

项目实际是「四层业务分层 + 一条横切能力 + 一层数据」：

```
┌─────────────────────────────────────────────────────────────┐
│ 用例层  test_cases/                                          │
│ 只做：调用页面业务方法 + 断言                                  │
│ 禁止：driver 操作、元素定位、显式等待                           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 传业务参数（账号、slug、期望值）
┌───────────────────────────▼─────────────────────────────────┐
│ 页面层  pages/                                               │
│ 只做：元素定位常量 + 业务方法组合                               │
│ 禁止：底层等待/点击实现、业务断言                               │
└───────────────────────────┬─────────────────────────────────┘
                            │ 传定位器 + 输入值 + 超时
┌───────────────────────────▼─────────────────────────────────┐
│ 基础层  base/base_page.py                                    │
│ 只做：查找/等待/点击/输入/弹窗/iframe/鼠标/JS/截图等原子能力    │
│ 禁止：任何业务语义（不知道什么是“登录”“购物车”）                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ WebDriver 协议
┌───────────────────────────▼─────────────────────────────────┐
│ 浏览器  Chrome / Firefox / Edge                               │
└─────────────────────────────────────────────────────────────┘

横切能力：utils/（日志、YAML、Allure、测试数据、录屏）
数据来源：config/env.yaml（地址、浏览器、账号、期望值、用例数据）
```

### 2.1 各层职责与「参数角色」

| 层 | 目录 | 核心职责 | 它接收什么参数 | 它返回什么 |
| --- | --- | --- | --- | --- |
| 用例层 | `test_cases/` | 组织业务调用顺序、断言 | fixture 对象、`parametrize` 的 `case_data`、模块级 `CONFIG` | 无（pytest 用例返回 None，靠 assert 表达结果） |
| 页面层 | `pages/` | 定位器 + 业务动作 | 业务参数（username/password/slug/id/first/last/zip）、可选 timeout | 页面对象自身或读取到的数据（str/int/list/dict/bool） |
| 基础层 | `base/` | Selenium 原子操作 | `locator` 元组、`text`、`timeout`、回调函数 | `WebElement` / `str` / `bool` / `int` / `dict` / `None` |
| 数据层 | `config/env.yaml` | 所有可变数据外置 | 无 | 被 YAML 解析成 Python `dict/list/str/int/bool` |
| 工具层 | `utils/` | 日志、配置读取、Allure、数据查询、录屏 | 文件路径、日志名、级别、附件内容 | logger / dict / 商品 dict / bool |
| 报告层 | `conftest.py` 钩子 + `generate_report.py` | 失败取证、报告生成 | pytest `item`/`report`、Allure JSON | 截图文件、GIF、HTML 报告 |

### 2.2 分层铁律

- 用例层**不出现** `driver.find_element(...)`，也不出现 `By.XXX`；
- 页面层**不出现** `WebDriverWait(...)`，全部复用 BasePage；
- 基础层**不出现**「登录」「购物车」这类业务词；
- 数据层**不出现**代码逻辑；
- 工具层**不反向依赖**页面层和用例层。

为什么要这么严？因为面试官问「你的框架怎么分层」时，你要能说出**依赖方向是单向的**：用例 → 页面 → 基础 → WebDriver。改一个元素定位，只改页面层；改等待策略，只改基础层；改用例数据，只改 YAML。上层不知道下层细节，这就是「解耦」。

## 3. 执行链路：从命令行到报告

### 3.1 静态调用链（代码之间的调用关系）

```
test_cases/test_login.py::TestLogin::test_login_success_standard_user
    │  函数参数 login_page（pytest 注入）
    ▼
conftest.py::login_page fixture
    │  config fixture → get_effective_config() → YAML dict
    │  driver fixture → webdriver.Chrome()
    ▼
pages/login_page.py::LoginPage.login_and_wait_inventory(username, password)
    │
    ├─ login(username, password)
    │    ├─ input_username(username) → BasePage.input_text(locator, text)
    │    ├─ input_password(password) → BasePage.input_text(locator, text)
    │    └─ click_login() → BasePage.click(locator)
    │
    └─ wait_inventory_loaded() → BasePage.find_element(locator)
         → WebDriverWait.until(EC.visibility_of_element_located(locator))
         → driver.find_element(By.CSS_SELECTOR, ".inventory_list")
```

### 3.2 一次完整 pytest 运行的生命周期

```
① 读配置
   pytest.ini
   ├─ testpaths = test_cases unit_tests         → 收集范围
   ├─ python_files = test_*.py                  → 哪些文件算用例
   ├─ python_classes = Test*                    → 哪些类算用例类
   ├─ python_functions = test_*                 → 哪些函数算用例
   ├─ pythonpath = .                            → 项目根加入 sys.path
   └─ addopts = --alluredir=... --clean-alluredir

② 加载 conftest.py（pytest 最先导入）
   ├─ LogUtil.setup()                           → 全局日志立即生效
   ├─ CONFIG = get_effective_config(...)        → 读 YAML + 环境变量覆写
   └─ 注册 --browser 命令行参数

③ 收集用例（collection）
   ├─ import 每个 test_*.py
   │    ├─ 模块级 CONFIG = get_effective_config()
   │    └─ @pytest.mark.parametrize 在收集阶段展开成多条 test item
   └─ 生成测试树：模块 → 类 → 方法 → 参数集

④ 执行每条用例（setup → call → teardown）
   setup：
      config fixture（function 级，深拷贝）
      driver fixture（function 级，启动浏览器）
      login_page fixture（打开登录页）
      inventory_page fixture（真实 UI 登录）
      cart_page fixture（加购 2 件 + 进购物车）
      checkout_* fixture（填表 + 进概览页）
   call：
      用例函数体：业务调用 + assert
   teardown（反向）：
      driver fixture：停止录屏 → driver.quit()
      其他 fixture：无显式 teardown，随 driver 结束

⑤ 失败钩子
   pytest_runtest_makereport
   ├─ 只在 when == "call" 且 failed 时触发
   ├─ item.funcargs.get("driver") 取 driver
   ├─ 截图 → reports/screenshots/
   ├─ 录屏 GIF → Allure 附件
   └─ 浏览器控制台日志 → Allure 附件

⑥ 会话结束
   reports/allure_results/*.json + environment.properties
   → generate_report.py 解析 JSON
   → reports/html-report/index.html（可发布 GitHub Pages）
```

### 3.3 五层视图（题目要求的文字版流程图）

把上面的链路按题目要求重新归类：

```
【前置准备层】
  命令行参数 --browser

        ▼
【用例层】
  test_cases/test_*.py

  @pytest.mark.parametrize = 数据矩阵（case_data / internal_path）
```

## 4. 参数流转总图：先把「水管」画出来

### 4.1 六种数据来源

| 来源 | 项目中的例子 | 什么时候用 | 面试关键词 |
| --- | --- | --- | --- |
| 代码常量 | 元素定位器 `(By.ID, "user-name")`、`MENU_TIMEOUT = 20` | 稳定不变的定位与算法常量 | 定位器集中管理 |
| 配置文件 | `config/env.yaml` 的账号、URL、期望文案 | 环境/数据可变，要外置 | 数据驱动、零硬编码 |
| 上一步返回值 | `get_product(4)["slug"]`、`get_summary_amounts()` 的 dict | 后一步依赖前一步的实际结果 | 参数依赖、返回值传递 |
| fixture | `driver`、`config`、`login_page`、`page_factory` | 跨多个步骤复用的对象/前置状态 | 依赖注入、作用域 |
| 命令行 | `--browser=chrome` | 运行期切换执行环境 | 命令行覆盖 |
| 环境变量 | `BASE_URL`、`HEADLESS`、`WAIT_TIMEOUT` | CI/本地不同环境，或敏感信息注入 | 优先级、配置覆盖 |
| 参数化数据 | `case_data`、`internal_path` | 同一测试逻辑跑多组数据 | `parametrize`、数据矩阵 |

> 注意：参数化数据本身也来自 YAML，但它在 **pytest 收集阶段** 就被展开成多条独立测试，和运行期读 YAML 是两种时机，面试要能区分。

### 4.2 一条用例的参数水管（以登录成功为例）

```

        ▼

        │  位置参数：username: str, password: str
        │  出参：None（副作用：页面跳转）
        ▼

        │
        │ ⑤ 用例读取页面返回值
        ▼

        │

        ▼

```

### 4.3 一个关键认知：参数在每一层「变少」

- YAML 里有很多字段，但 `driver` fixture 只关心 `browser` 和 `timeout`；
- `LoginPage` 不关心账号叫什么，它只接收 `username/password` 两个字符串；
- `BasePage.input_text` 更不关心业务，它只接收 `locator` 和 `text`；
- 到了 Selenium，只剩 `find_element(by, value)` 和 `send_keys(text)`。

**好的参数设计是逐层收窄的**：每一层只暴露自己真正需要的参数，不把整份配置 dict 到处传。这就是为什么本项目页面层不接收 `config`，只接收具体的值（`open_about_and_navigate(url_prefix)` 的文档里也明确写了「页面层不读配置」）。

## 5. 从 0 搭建：一步一步来

下面按「先解决什么问题 → 直白版 → 发现问题 → 重构版 → 参数拆解」的顺序讲。不要一上来就背最终代码，先理解每一步为什么存在。

### Step 0：目录结构先立起来

**要解决的问题**：代码放哪里？谁依赖谁？测试数据和代码怎么分开？

```
sauce-ui-autotest/
├── base/base_page.py          # 基础层：Selenium 原子操作
├── pages/                     # 页面层：元素定位 + 业务方法
│   ├── locators.py            # 跨页面复用的定位器（唯一来源）
│   ├── login_page.py
│   ├── inventory_page.py
│   ├── item_page.py
│   ├── cart_page.py
│   ├── checkout_page.py
│   └── menu_page.py
├── test_cases/                # 用例层：业务调用 + 断言
├── config/env.yaml            # 数据层
├── utils/                     # 工具层
├── conftest.py                # fixture + 钩子 + 命令行参数
├── pytest.ini
├── requirements.txt
└── README.md
```

**参数视角**：目录结构本身就是一种「参数边界」。数据只在 `config/`，对象只在 `pages/`，能力只在 `base/`。如果你把账号写进 `test_login.py`，参数就从「外部配置」退化成了「代码常量」，换环境就要改代码。

---

### Step 1：先有数据层 `config/env.yaml`

**要解决的问题**：URL、账号、密码、期望文案、商品价格……这些东西会变。如果写死在代码里，每换一个环境就要改代码、重新提交，而且测试数据和测试逻辑混在一起，没法复用。

**直白版（错误示范）**：

```python
# 不要这样写
def test_login():
    driver.get("https://www.saucedemo.com/")
    driver.find_element(By.ID, "user-name").send_keys("standard_user")
    driver.find_element(By.ID, "password").send_keys("secret_sauce")
    driver.find_element(By.ID, "login-button").click()
    assert "inventory" in driver.current_url
```

问题：

- 地址、账号、密码全写死；
- 换测试环境要改代码；
- 断言里的期望值也写死，数据一变就要改多处；
- 无法做多组数据参数化。

**重构版（项目实际结构，节选）**：

```yaml
# config/env.yaml
env:
  name: "test"                              # 环境名称

base_url: "https://www.saucedemo.com/"      # 被测系统入口

urls:
  inventory: "https://www.saucedemo.com/inventory.html"
  cart: "https://www.saucedemo.com/cart.html"

browser:
  name: "chrome"
  headless: false
  window_size: "1920,1080"
  page_load_timeout: 30

timeout:
  explicit_wait: 10
  poll_frequency: 0.5
  glitch_wait: 20

accounts:
  standard: {username: "standard_user", password: "secret_sauce"}
  locked:   {username: "locked_out_user", password: "secret_sauce"}

expected:
  products_title: "Products"
  inventory_item_count: 6
  error_messages:
    locked: "Epic sadface: Sorry, this user has been locked out."
    username_required: "Epic sadface: Username is required"

products:
  - {slug: "sauce-labs-backpack", id: 4, name: "Sauce Labs Backpack", price: "29.99"}
  - {slug: "sauce-labs-bike-light", id: 0, name: "Sauce Labs Bike Light", price: "9.99"}

login_cases:
  required_field_cases:
    - name: "空用户名+空密码登录"
      case_id: "SAUCE-LOGIN-004"
      username: ""
      password: ""
      expected_error: "username_required"
      severity: "critical"
```

**【参数相关注释】**

- `base_url`：后续被 `login_page` fixture 读取，传给 `page.open_url(url)`；
- `urls.inventory`：被断言直接读取，作为「期望 URL」；
- `browser.*`：被 `driver` fixture 读取，决定启动哪个浏览器、是否无头、页面加载超时；
- `timeout.*`：被 `BasePage.__init__` 和各个 fixture 读取，作为显式等待的默认预算；
- `accounts.*`：被用例读取成 dict，再拆成 `username` / `password` 两个位置参数；
- `expected.*`：断言的「基准值」，和页面读出来的「实际值」比较；
- `products[*]`：商品四元组（slug/id/name/price），是后续动态定位器和期望值的数据源；
- `login_cases.required_field_cases`：一个 **list[dict]**，被 `@pytest.mark.parametrize` 消费，每组 dict 变成一条独立测试；
- YAML 里的 `""`：不是 None，是空字符串。项目用它表达「这个字段不输入」，见 `login_cases` 和 `invalid_field_cases`。

**为什么用 YAML 而不是 Excel/JSON/CSV？**

- YAML 天生支持嵌套、列表、锚点复用，可读性好；
- `safe_load` 安全；
- 这份项目的数据量不大，YAML 足够；Excel 更适合大量业务用例和产品同学维护，但解析成本高。

**YAML 锚点（容易忽略的复用参数）**：

```yaml
expected:
  product_names: &AZ_NAMES        # 定义锚点
    - "Sauce Labs Backpack"
    - "Sauce Labs Bike Light"

sort_expected:
  az_names: *AZ_NAMES             # 引用同一个列表
```

`&AZ_NAMES` 定义、`*AZ_NAMES` 引用，避免同一份商品名写两遍。面试若问「数据驱动怎么避免重复数据」，可以提锚点。

### Step 2：读取层 `utils/yaml_util.py` + `utils/config_util.py`

**要解决的问题**：YAML 不能直接被 Python 用，需要读取；但读取不能每个用例都 `open()` 一次，也不能让一个用例改了配置影响其他用例。

#### 2.1 直白版

```python
import yaml

def read_config(path):
    with open(path, "r", encoding="utf-8") as f:
        return yaml.safe_load(f)
```

能跑，但有问题：

- 每次调用都读磁盘，测试多了浪费；
- 相对路径依赖启动目录，换个目录运行就找不到文件；
- 文件不存在/语法错误时，报的是底层异常，不好排查；
- 返回的是 `yaml.safe_load` 的新对象，这一点还好；但如果加了缓存，直接返回缓存对象，调用方一改就污染所有人。

#### 2.2 重构版：`YamlUtil`（单例 + 缓存 + 深拷贝）

```python
class YamlUtil:
    _instance = None

    def __new__(cls, *args, **kwargs):
        # 【参数】*args/**kwargs：这里不接收具体配置参数，只是为了兼容
        #        任意构造方式，保证 YamlUtil() 永远返回同一个实例
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self):
        # 【参数】__init__ 无显式入参；每次 YamlUtil() 都会调用 __init__，
        #        所以用 hasattr 防止缓存被反复清空
        if not hasattr(self, "_cache"):
            self._cache = {}

    def read_yaml(self, file_path):
        # 【入参】file_path：str 或 pathlib.Path，绝对路径或基于项目根目录的相对路径
        # 【出参】Any：YAML 解析后的 Python 对象（通常是 dict / list）
        path = Path(file_path)
        if not path.is_absolute():
            path = PROJECT_ROOT / path       # 相对路径统一基于项目根目录

        key = str(path.resolve())            # 缓存 key 用绝对路径，防止不同写法重复缓存
        if key not in self._cache:
            if not path.exists():
                raise FileNotFoundError(f"[数据层错误] YAML 文件不存在: {path}")
            with open(path, "r", encoding="utf-8") as f:
                self._cache[key] = yaml.safe_load(f)
        data = self._cache[key]
        if data is None:
            raise ValueError(f"[数据层错误] YAML 文件内容为空: {path}")
        return copy.deepcopy(data)           # 关键：返回独立副本
```

**【参数相关注释】**

- `file_path` 是**位置参数**，调用方可以传绝对路径或相对路径；
- 相对路径不是相对于当前工作目录，而是相对于 `PROJECT_ROOT`，这是为了「从任何目录启动 pytest 都能找到配置」；
- 缓存 key 是 `resolve()` 后的绝对路径，不是原始字符串，避免 `config/env.yaml` 和 `./config/env.yaml` 被当成两个文件；
- **返回深拷贝**：这是参数隔离的关键。调用方拿到的是自己的副本，改它不会改缓存；
- 异常类型是显式的 `FileNotFoundError` / `ValueError`，比底层 IO 异常更容易定位。

#### 2.3 环境覆写：`utils/config_util.py`

```python
def get_effective_config(file_path=CONFIG_PATH) -> dict:
    # 【入参】file_path：默认值 CONFIG_PATH（默认参数）
    # 【出参】dict：完整配置的独立副本
    config = YamlUtil().read_yaml(file_path)   # read_yaml 已返回深拷贝
    _apply_wait_timeout(config)                 # 原地修改这份副本
    _apply_base_url(config)                     # 原地修改这份副本
    return config
```

`_apply_base_url` 的逻辑值得单独理解：

```python
def _apply_base_url(config: dict) -> None:
    base_url_env = (os.environ.get("BASE_URL") or "").strip()
    if not base_url_env:
        return
    old_base = str(config["base_url"]).rstrip("/")
    new_base = base_url_env.rstrip("/")
    config["base_url"] = new_base + "/"
    for url_key, url_value in config.get("urls", {}).items():
        # 【参数】url_key / url_value 是 dict.items() 解包出来的键值对
        if isinstance(url_value, str) and url_value.startswith(old_base):
            config["urls"][url_key] = new_base + url_value[len(old_base):]
```

**【参数相关注释】**

- `BASE_URL` 从环境变量来，优先级高于 YAML；
- 不仅替换 `base_url`，还把 `urls` 里所有以旧域名开头的地址同步替换，保留路径和查询参数；
- 这样 CI 跑本地站点时，只需要设一个 `BASE_URL=http://127.0.0.1:8000/`，所有断言不用改；
- 函数返回 `None`，通过**原地修改传入的 dict** 产生副作用。这是一种「输出参数（out parameter）」风格，调用方必须知道传进去的 dict 会被改。

**优先级总结（务必背下来）**：

| 配置项 | 优先级从高到低 |
| --- | --- |
| 浏览器 | 命令行 `--browser` > `env.yaml` 的 `browser.name` |
| 无头模式 | 环境变量 `HEADLESS` > `env.yaml` 的 `browser.headless` |
| 显式等待 | 环境变量 `WAIT_TIMEOUT` > CI 默认 30s > `env.yaml` 的 `timeout.explicit_wait` |
| 测试地址 | 环境变量 `BASE_URL` > `env.yaml` 的 `base_url/urls` |
| 录屏 | 环境变量 `RECORDING=false` > `env.yaml` 的 `recording.enabled` |
| Edge 驱动 | 环境变量 `EDGE_DRIVER_PATH` > Selenium Manager 自动管理 |

**直白版 vs 重构版对比**：

| 维度 | 直白版 `read_config` | 重构版 `get_effective_config` |
| --- | --- | --- |
| 读取次数 | 每次调用都读盘 | 同一文件只解析一次（缓存） |
| 路径 | 依赖当前工作目录 | 统一基于项目根目录 |
| 数据污染 | 返回缓存对象会被改 | 深拷贝，互不影响 |
| 环境切换 | 只能改文件 | 环境变量覆写 |
| 错误提示 | 底层异常 | 中文业务异常 |

### Step 3：基础层 `base/base_page.py`

**要解决的问题**：每个页面都要「找元素 → 等可见 → 点击 → 输入 → 失败截图」。如果每个测试都写一遍，代码重复、等待策略不统一、失败现场丢失。

#### 3.1 直白版：直接调用 Selenium

```python
from selenium.webdriver.common.by import By

driver.get("https://www.saucedemo.com/")
driver.find_element(By.ID, "user-name").send_keys("standard_user")
driver.find_element(By.ID, "password").send_keys("secret_sauce")
driver.find_element(By.ID, "login-button").click()
```

**这段代码能跑，但存在四个问题**：

1. 元素还没渲染出来就查找，会偶发 `NoSuchElementException`；
2. 点击前没有等「可点击」，元素被遮挡时点击无效；
3. 失败时没有截图、没有页面源码，无法复现；
4. 每个用例都重复写，改等待策略要改 N 处。

#### 3.2 第一次重构：包一个类

```python
class BasePage:
    def __init__(self, driver):
        self.driver = driver          # 【入参】driver：WebDriver 实例，由 fixture 创建并传入
```

这样页面对象可以共享同一个 driver，但还没有解决等待和失败取证。

#### 3.3 最终版：注入 driver + 等待策略

```python
class BasePage:
    DEFAULT_TIMEOUT = 10
    DEFAULT_POLL_FREQUENCY = 0.5

    def __init__(self, driver: WebDriver,
                 timeout: int = DEFAULT_TIMEOUT,
                 poll_frequency: float = DEFAULT_POLL_FREQUENCY):
        # 【入参 1】driver：WebDriver，来源是 conftest 的 driver fixture
        # 【入参 2】timeout：int，秒；来源是 config["timeout"]["explicit_wait"]
        # 【入参 3】poll_frequency：float，秒；来源是 config["timeout"]["poll_frequency"]
        # 【出参】无（构造函数返回实例本身）
        self.driver = driver
        self.timeout = timeout
        self.poll_frequency = poll_frequency
```

这三个参数为什么放在构造函数里？

- `driver` 是页面对象的「生命线」，所有操作都要用；
- `timeout/poll_frequency` 是这一整类操作的默认策略，放进实例，避免每个方法都传；
- 但方法层仍保留 `timeout=None` 的可选参数，允许单次覆盖（例如菜单动画给 20s）。

这就是「**默认值 + 局部覆盖**」的参数设计：常用的走默认，特殊的单独传。

#### 3.4 核心方法逐行拆解

**（1）`_wait`：统一构造显式等待**

```python
def _wait(self, timeout: Optional[int] = None) -> WebDriverWait:
    # 【入参】timeout：Optional[int]，None 表示用实例默认值，显式传 0 表示单次探测
    # 【出参】WebDriverWait 对象，供 .until(...) 使用
    wait_timeout = self.timeout if timeout is None else timeout
    return WebDriverWait(self.driver, wait_timeout, self.poll_frequency)
```

这里的 `if timeout is None` 而不是 `timeout or self.timeout` 是刻意的：

- `timeout=0` 是合法值，表示「只探测一次，不等待」；
- 如果用 `or`，`0` 会被当成假值，回退成默认 10s，导致「即时探测」变成「空转 10 秒」。

面试点：**默认值参数用 `None` 做哨兵，而不是用 `0`/`""` 做哨兵，因为 0 和空串可能是合法输入。**

**（2）`find_element`：等待可见后返回元素**

```python
def find_element(self, locator: Locator, timeout: Optional[int] = None) -> WebElement:
    # 【入参】locator：Tuple[str, str]，如 (By.ID, "user-name")
    # 【入参】timeout：Optional[int]，单次覆盖等待预算
    # 【出参】WebElement：找到的元素对象，供后续 .click()/.text/.get_attribute() 使用
    try:
        return self._wait(timeout).until(EC.visibility_of_element_located(locator))
    except TimeoutException as exc:
        raise self._find_timeout(locator, timeout, "仍不可见") from exc
```

**【参数相关注释】**

- `locator` 是**位置参数**，类型是二元组，不是两个分开的参数；
- `ec.visibility_of_element_located(locator)` 接收的也是这个二元组；
- 失败时 `_find_timeout` 返回一个新的 `TimeoutException`，再用 `raise ... from exc` 保留原始异常链。

**（3）`find_elements`：注意 `*locator` 解包**

```python
def find_elements(self, locator: Locator, timeout: Optional[int] = None) -> List[WebElement]:
    self._wait(timeout).until(EC.presence_of_all_elements_located(locator))
    return self.driver.find_elements(*locator)
    #                                   ^^^^^^^^ 解包成两个位置参数
    # 等价于 driver.find_elements(By.CSS_SELECTOR, ".inventory_item")
```

面试点：Selenium 4 的 `find_element(by, value)` 接收两个参数，而项目里统一用 `(by, value)` 元组保存定位器，所以调用时要 `*locator` 解包。忘了 `*` 就会变成 `find_element((By.ID, "x"),)`，参数数量不对。

**（4）`click`：等待可点击 + 失败截图**

```python
def click(self, locator: Locator, timeout: Optional[int] = None) -> None:
    # 【入参】locator：定位器元组
    # 【入参】timeout：可选的单次等待预算
    # 【出参】None；副作用是点击元素，失败时截图并抛异常
    element = self.find_element_clickable(locator, timeout)
    try:
        element.click()
    except Exception as exc:
        self.save_screenshot("click_fail")
        raise
```

**（5）`input_text`：输入 + 回读校验 + JS 兜底**

```python
def input_text(self, locator: Locator, text: str, clear_first: bool = True) -> None:
    # 【入参】locator：输入框定位器
    # 【入参】text：str，要输入的文本；来源可能是账号、表单数据、超长串
    # 【入参】clear_first：bool，默认 True；是否先清空输入框
    # 【出参】None
    target = text or ""                 # 防御 None：None 当作空串处理
    for attempt in range(3):
        element = self.find_element(locator)
        if clear_first:
            element.clear()
        element.send_keys(text)
        if self._wait_input_value(locator, target, timeout=3):
            return
    if self._set_value_by_js(locator, target):
        return
    raise ValueError(f"输入值回读校验失败: {locator}")
```

**为什么需要 `clear_first`？**

- 登录失败用例要验证「输入未被清空」，这时候框架自己不清理；
- 结算表单每次填值前要清空，避免上一次残留；
- 参数化时同一个页面可能被复用，必须明确「覆盖」还是「追加」。

**为什么输入后要回读？**

React 受控组件在无头 Chrome 下偶发「键盘事件被吞」：`send_keys` 返回成功，但页面状态没更新。回读 `value` 属性可以确认输入真的生效；不生效就重输，再不行用 JS 原生 setter + 派发 `input/change` 事件兜底。

**（6）`click_robust`：把「成功条件」作为参数传进来**

这是全项目最值得讲的参数设计之一：

```python
def click_robust(self,
                 locator: Locator,
                 success: Callable[[], bool],
                 timeout: int = 10,
                 js_timeout: int = 5,
                 retries: int = 1,
                 fail_message: str = "点击后未达到成功条件",
                 post_js_recheck: Optional[Callable[[], bool]] = None,
                 retry_allowed: Optional[Callable[[], bool]] = None,
                 before_retry: Optional[Callable[[], None]] = None,
                 on_final_failure: Optional[Callable[[], Optional[bool]]] = None) -> None:
    # 【入参 locator】要点击的元素
    # 【入参 success】无参回调，返回 bool：点击是否真正生效
    # 【入参 timeout】原生点击后等待成功条件的预算
    # 【入参 js_timeout】JS 点击后等待成功条件的预算
    # 【入参 retries】重试次数（默认 1，即最多执行 2 轮）
    # 【入参 fail_message】最终失败时的中文信息
    # 【入参 post_js_recheck】JS 点击仍未生效时的页面级复核（如刷新）
    # 【入参 retry_allowed】是否允许重试（如按钮还在页面）
    # 【入参 before_retry】重试前的准备（如重新展开菜单）
    # 【入参 on_final_failure】最终兜底（如 URL 直达）；返回 True 表示已接管
    # 【出参】None；失败抛 TimeoutException
```

**为什么不能只传 locator？**

因为「点击成功」在不同页面有不同定义：

- 加购成功 = Remove 按钮出现；
- 进入购物车成功 = URL 包含 `/cart.html`；
- 退出登录成功 = 登录页 `user-name` 输入框可见；
- 结算提交成功 = Finish 按钮出现 **或** 校验错误提示出现。

BasePage 不可能知道这些业务语义，所以把「判断成功的函数」作为参数传进来。这是**回调参数 / 策略参数**：调用方决定「什么叫成功」，基础层只负责「点、等、兜底、重试」。

**`*args` 的用法**：

```python
def execute_script(self, script: str, *args):
    # 【入参】script：JS 脚本字符串
    # 【入参】*args：可变位置参数，会原样传给 Selenium
    # 【出参】JS 的返回值（可能是 str/dict/list/None）
    return self.driver.execute_script(script, *args)
```

调用：

```python
self.execute_script("arguments[0].click();", element)
#                                    ^^^^^^^ 这个 element 进入 *args
```

**直白版 vs 重构版对比**：

| 维度 | 直白 Selenium | BasePage |
| --- | --- | --- |
| 等待 | 无 / `sleep` | 显式等待，条件明确 |
| 点击 | `element.click()` | 等可点击 + 失败截图 + JS 兜底 |
| 输入 | `send_keys` | 清空 + 回读 + 重输 + JS setter |
| 失败现场 | 无 | 截图 + 页面源码附件 |
| 复用 | 每处重复 | 所有页面继承 |
| 业务语义 | 混在测试里 | 基础层不含业务，页面层组合 |

### Step 4：页面层 Page Object

**要解决的问题**：用例不应该知道「用户名输入框的 id 是 user-name」。元素改版时，只改页面层；用例只表达业务动作。

#### 4.1 直白版

```python
def test_login(driver):
    driver.get("https://www.saucedemo.com/")
    driver.find_element(By.ID, "user-name").send_keys("standard_user")
    driver.find_element(By.ID, "password").send_keys("secret_sauce")
    driver.find_element(By.ID, "login-button").click()
    assert driver.current_url == "https://www.saucedemo.com/inventory.html"
```

问题：

- 用例知道三个定位器；
- 没有等待；
- 登录流程在每条用例里重复；
- 换一个页面就要重新学一套定位。

#### 4.2 重构版：LoginPage

```python
class LoginPage(BasePage):
    USERNAME_INPUT = (By.ID, "user-name")
    PASSWORD_INPUT = (By.ID, "password")
    LOGIN_BUTTON = (By.ID, "login-button")

    def input_username(self, username: str) -> None:
        # 【入参】username：str，来源是 env.yaml 的 accounts.*.username
        # 【出参】None
        self.input_text(self.USERNAME_INPUT, username)

    def input_password(self, password: str) -> None:
        # 【入参】password：str，来源是 env.yaml 的 accounts.*.password
        self.input_text(self.PASSWORD_INPUT, password)

    def click_login(self) -> None:
        # 【入参】无
        self.click(self.LOGIN_BUTTON)

    def login(self, username: str, password: str) -> None:
        # 【入参】username/password：两个 str，位置参数
        # 【出参】None；副作用是登录表单被提交
        self.input_username(username)
        self.input_password(password)
        self.click_login()
```

**【参数相关注释】**

- 页面层方法的参数是**业务参数**，不是定位器。用例传「账号密码」，页面层自己决定用哪个定位器；
- `username/password` 用位置参数，因为这个方法的语义非常明确，调用方不会搞混；
- 如果参数变多、类型相同（如 `first/last/zip` 都是 str），就建议用关键字参数，防止顺序写错（项目里 `fill_info(first, last, zip_code)` 目前是位置参数，调用时要小心）。

#### 4.3 动态定位器：slug 作为参数

有些元素的 `data-test` 是动态拼接的，比如加购按钮：

```html
<button data-test="add-to-cart-sauce-labs-backpack">Add to cart</button>
```

所以页面层提供：

```python
@staticmethod
def add_button(slug: str) -> tuple:
    # 【入参】slug：str，商品短标识，来源是 get_product(id)["slug"]
    # 【出参】Tuple[str, str]，如 (By.CSS_SELECTOR, "[data-test='add-to-cart-sauce-labs-backpack']")
    return (By.CSS_SELECTOR, f"[data-test='add-to-cart-{slug}']")
```

调用：

```python
backpack = get_product(4)                 # 出参：dict
slug = backpack["slug"]                   # 出参：str
inventory_page.add_to_cart(slug)          # 入参：str
```

**数据流**：`商品 id (int)` → `get_product` → `商品 dict` → `slug (str)` → `add_button` → `locator (tuple)` → `click` → 页面状态变化。

**为什么用 `@staticmethod`？**

- 这个方法不需要 `self`，它只根据 `slug` 拼字符串；
- 如果写成普通方法，`inventory_page.add_button(slug)` 会自动把 `self` 作为第一个参数，变成 `add_button(self, slug)`，参数错位；
- 用 `staticmethod` 明确「这个函数不依赖实例」。

**`CartPage` 的一个真实坑**：

```python
class CartPage(BasePage):
    # 必须 staticmethod 包装：直接赋值会把普通函数绑定为本类方法，多传 self 参数
    remove_button = staticmethod(InventoryPage.remove_button)
```

如果写成：

```python
remove_button = InventoryPage.remove_button   # 错误！
```

此时 `InventoryPage.remove_button` 取到的是普通函数，赋给 `CartPage` 后变成 `CartPage` 的方法；调用 `cart_page.remove_button(slug)` 会变成 `remove_button(self, slug)`，参数数量不对。这是「描述符绑定」的坑，面试问「staticmethod 和普通方法区别」时可以拿这个例子。

#### 4.4 页面层的返回值设计

页面层的方法分两类：

1. **动作类**：返回 `None`，靠页面状态变化体现结果。
   ```python
   def add_to_cart(self, slug: str, retries: int = 1) -> None:
       ...
   ```
2. **读取类**：返回数据，供用例断言或下一步使用。
   ```python
   def get_product_names(self) -> list:
       return [element.text for element in self.find_elements(self.INVENTORY_ITEM_NAME)]
   ```

**动作类为什么不返回元素/布尔值？**

- 返回元素会让用例重新耦合底层对象；
- 返回布尔值会把「成功判定」提前固化在页面层，失去灵活性；
- 项目采用「动作 + 显式等待成功条件」的方式：动作方法内部等状态变化，失败抛异常；用例只关心「动作完成后读什么、断言什么」。

**读取类返回值会流向哪里？**

- `get_product_names()` → 用例直接和 `CONFIG["sort_expected"]["az_names"]` 比较；
- `get_product_image_srcs()` → 用例做 `set()` 去重，断言唯一数；
- `get_summary_amounts()` → 用例做 Decimal 运算；
- `get_cookie()` → 用例判断登录态。

### Step 5：`conftest.py` fixture 前置链

**要解决的问题**：每条用例都要「启动浏览器 → 打开登录页 → 登录 → 加购 → 进购物车」。如果每个用例都写一遍，重复且容易漏。fixture 把这些前置步骤封装起来，用例只需要在函数参数里「点名」。

#### 5.1 直白版：每个用例自己 setup

```python
def test_cart():
    driver = webdriver.Chrome()
    driver.get("https://www.saucedemo.com/")
    driver.find_element(By.ID, "user-name").send_keys("standard_user")
    driver.find_element(By.ID, "password").send_keys("secret_sauce")
    driver.find_element(By.ID, "login-button").click()
    # ... 加购、进购物车 ...
    driver.quit()
```

问题：

- 重复；
- 忘记 `quit()` 会泄漏浏览器进程；
- 失败时不会自动截图；
- 前置步骤和测试逻辑混在一起，用例很长。

#### 5.2 最小 fixture

```python
@pytest.fixture
def driver():
    d = webdriver.Chrome()
    yield d               # yield 之前是 setup，yield 之后是 teardown
    d.quit()

def test_login(driver):   # 参数名 = fixture 名，pytest 自动注入
    driver.get("...")
```

**参数机制**：pytest 看到测试函数的参数名 `driver`，就去 fixture 注册表里找同名 fixture，调用它，把返回值注入函数。**参数名必须和 fixture 名完全一致**，这不是普通函数调用，是依赖注入。

#### 5.3 项目实际 fixture 链

```
config（function）
  └─ driver（function，依赖 config）
       └─ login_page（function，依赖 driver + config）
            └─ inventory_page（function，依赖 login_page + page_factory + config）
                 └─ cart_page（function，依赖 inventory_page + page_factory + config）
                      └─ checkout_step_one_page（function，依赖 cart_page + page_factory + config）
                           └─ checkout_overview_page（function，依赖 checkout_step_one_page + config）

page_factory（function，依赖 driver + config）——旁路工厂，任意页面按需创建
```

**关键参数拆解**：

```python
@pytest.fixture(scope="function")
def config():
    # 【入参】无
    # 【出参】dict：每次调用返回一份独立的生效配置副本
    return get_effective_config(CONFIG_PATH)


@pytest.fixture(scope="function")
def driver(request, config):
    # 【入参 request】pytest 内置 fixture，用来读命令行参数、挂载节点属性
    # 【入参 config】上面定义的 fixture，pytest 按参数名注入
    # 【出参】WebDriver 实例（yield 出去）
    browser_name = request.config.getoption("--browser")
    browser_conf = config["browser"]
    headless = is_headless(browser_conf)
    page_load_timeout = browser_conf["page_load_timeout"]
    ...
    yield driver_obj          # 用例执行期间拿到 driver
    recorder.stop()
    driver_obj.quit()         # teardown 一定执行


@pytest.fixture(scope="function")
def login_page(driver, config):
    # 【入参】driver/config：pytest 注入
    # 【出参】LoginPage 实例（已经打开登录页）
    page = LoginPage(
        driver,
        timeout=config["timeout"]["explicit_wait"],
        poll_frequency=config["timeout"]["poll_frequency"],
    )
    page.open_url(config["base_url"])
    return page


@pytest.fixture(scope="function")
def page_factory(driver, config):
    # 【入参】driver/config：pytest 注入
    # 【出参】一个函数 _create，供用例调用创建任意页面对象
    def _create(page_class, **kwargs):
        # 【入参 page_class】页面类本身（如 InventoryPage）
        # 【入参 **kwargs】额外构造参数，原样转发
        # 【出参】page_class 的实例，已注入 driver 和统一等待策略
        return page_class(
            driver,
            timeout=config["timeout"]["explicit_wait"],
            poll_frequency=config["timeout"]["poll_frequency"],
            **kwargs
        )
    return _create
```

**`page_factory` 是「返回函数的 fixture」**：

- `page_factory` 本身是一个 fixture，出参是一个函数 `_create`；
- 用例调用 `page_factory(InventoryPage)`，相当于调用 `_create(InventoryPage)`；
- `_create` 通过闭包捕获 `driver/config`，所以不需要每次传；
- `**kwargs` 允许未来给页面类加构造参数，不用改工厂签名。

**为什么用工厂，而不是给每个页面都写一个 fixture？**

- 页面多的时候，fixture 会爆炸；
- 有些页面只在个别用例里用（如 `MenuPage`、`ItemPage`），没必要全局注册；
- 工厂模式让「创建页面对象」变成一个普通函数调用，灵活。

#### 5.4 fixture 作用域与缓存

- 全部是 `scope="function"`：每条用例都新建 driver、重新登录、重新加购；
- 同一测试内，多个 fixture 依赖同一个 `driver`，pytest 会**缓存**本次测试的 fixture 实例，不会重复启动浏览器；
- 测试结束后，fixture 按依赖的**反向顺序** teardown；
- 这样做的好处：用例完全隔离，登录态、购物车、Cookie 互不污染；缺点是慢（每条用例一个浏览器），所以项目用 xdist 并行来补速度。

**面试追问「为什么不用 session 级 driver？」**：

> session 级 driver 会快很多，但所有用例共享登录态和 localStorage，一条用例改了购物车会影响下一条；用例顺序一变就失败；并行时还会争抢同一个 driver。本项目选择 function 级隔离，用并行换回速度，稳定性优先。如果确实要复用登录态，可以用 session 级 storage_state/cookie，但必须每条用例显式重置状态，并接受顺序依赖。

#### 5.5 `request.node` 的「旁路参数传递」

```python
request.node._screen_recorder = recorder
```

- `request.node` 是当前测试节点；把录屏器挂在节点上；
- 失败钩子 `pytest_runtest_makereport(item, call)` 里用 `getattr(item, "_screen_recorder", None)` 取回来；
- 这不是普通函数参数，而是**通过 pytest 节点对象传递上下文**。面试问「fixture 里的对象怎么给钩子用」时可以答这个。

### Step 6：用例层

**要解决的问题**：把「业务调用」和「断言」组织成可读、可维护、可参数化的测试。

#### 6.1 直白版

```python
def test_login_success(login_page):
    login_page.login("standard_user", "secret_sauce")
    assert login_page.get_current_url() == "https://www.saucedemo.com/inventory.html"
    assert login_page.get_inventory_item_count() == 6
```

能跑，但：

- 账号密码、URL、期望数量写死；
- 登录后没有等商品列表加载；
- 没有步骤信息，报告里看不出做到哪一步；
- 无法复用到其他账号。

#### 6.2 项目版

```python
@pytest.mark.smoke
def test_login_success_standard_user(self, login_page):
    # 【入参 login_page】fixture 注入，类型 LoginPage
    account = CONFIG["accounts"]["standard"]      # 【出参】dict
    with allure.step("输入账号密码并登录（登录被拒绝时自动重试）"):
        login_page.login_and_wait_inventory(
            account["username"],                  # 【入参】str，来自 YAML
            account["password"],                  # 【入参】str，来自 YAML
        )
    with allure.step("断言1-URL跳转到商品列表页"):
        assert login_page.get_current_url() == CONFIG["urls"]["inventory"]
    with allure.step("断言2-展示6个商品"):
        assert login_page.get_inventory_item_count() == CONFIG["expected"]["inventory_item_count"]
    ...
```

**【参数相关注释】**

- 测试函数的参数 `self, login_page`：`self` 是类方法隐式参数，`login_page` 是 fixture 注入；
- `account["username"]` / `account["password"]`：从模块级 `CONFIG` 读取，位置参数传给页面方法；
- `CONFIG["urls"]["inventory"]`：期望 URL，直接参与断言；
- 断言里的「实际值」来自页面方法返回值，「期望值」来自 YAML；这就是断言的参数来源。

#### 6.3 参数化：一组数据 = 一条独立用例

```python
@pytest.mark.parametrize(
    "case_data",                                        # 参数名
    CONFIG["login_cases"]["required_field_cases"],      # 数据源：list[dict]
    ids=[case["case_id"] for case in CONFIG["login_cases"]["required_field_cases"]],
)
def test_login_required_field_validation(self, login_page, case_data):
    # 【入参 case_data】dict，由 parametrize 注入，每组数据一条测试
    allure.dynamic.title(case_data["name"])
    set_severity_from_str(case_data["severity"])
    login_page.login(case_data["username"], case_data["password"])
    assert login_page.get_error_message() == ERROR_MSGS[case_data["expected_error"]]
```

**参数机制拆解**：

- `"case_data"` 是**参数名**，必须和测试函数里的形参同名；
- 第二个参数是 `list[dict]`，pytest 会为每个 dict 生成一条测试；
- `ids` 是显示名列表，长度必须和数据组数一致；
- 每条测试拿到的 `case_data` 是那组 dict，用例内部再拆字段；
- 这是「**数据驱动**」：测试逻辑一份，数据 N 组。

**`ids` 的作用**：报告和命令行里显示 `test_login_required_field_validation[SAUCE-LOGIN-004]`，比默认的 `[case_data0]` 可读。

**参数化 vs 循环**：

```python
# 不推荐：一个测试里循环 3 组数据
def test_login_required(login_page):
    for case in cases:
        login_page.login(...)
        assert ...

# 推荐：parametrize 展开成 3 条独立测试
@pytest.mark.parametrize("case_data", cases)
def test_login_required(login_page, case_data):
    ...
```

区别：循环版本中途失败会中断，报告里只有一条用例；parametrize 每条独立，失败互不影响，报告可逐条追溯。

#### 6.4 断言层

项目里的断言分三种：

1. **硬断言**：`assert 实际 == 期望`，失败即用例失败；
2. **软断言/记录型**：采样值写入 Allure 附件，只有配置开关打开时才升级为硬断言（如 `visual_position_strict`、`require_image_alt_nonempty`）；
3. **等待即断言前置**：先 `wait_badge_text("2")` 等状态收敛，再 `assert get_badge_text() == "2"`；等待避免「刚点击还没渲染就断言」的竞态。

**断言参数的两个来源**：

- 实际值：页面读取方法（`get_*` / `is_*`）；
- 期望值：YAML（`expected` / `checkout` / `e2e` 等）。

### Step 7：报告层

**要解决的问题**：用例失败后，怎么知道失败在哪、页面长什么样、前端有没有报错。

三个机制：

1. **失败截图**：`pytest_runtest_makereport` 钩子，在 `call` 阶段失败且 fixture teardown 之前执行；
2. **失败录屏**：`ScreenRecorder` 后台线程周期截图，环形缓冲，失败时合成 GIF；
3. **Allure 附件**：截图、GIF、浏览器控制台日志、页面源码、采样值。

**钩子的参数**：

```python
@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    # 【入参 item】当前测试项，可访问 item.funcargs / item.name / 自定义属性
    # 【入参 call】当前执行阶段信息（setup/call/teardown）
    outcome = yield                    # hookwrapper 固定写法：先让其他钩子执行
    report = outcome.get_result()      # 拿到测试报告对象
    if report.when == "call" and report.failed:
        driver_instance = item.funcargs.get("driver")
        # 【参数】driver 是从当前测试的 fixture 缓存里取的，不是全局变量
        ...
```

**为什么用 `item.funcargs.get("driver")` 而不是全局 driver？**

- 每条用例的 driver 是独立的，全局变量会拿错；
- `item.funcargs` 是当前测试的 fixture 值字典，取到的就是这条用例的 driver；
- 用 `.get()` 而不是 `[]`，是为了在用例没有请求 driver 时返回 None，不抛 KeyError。

**报告链路**：

```
allure-pytest 写入 reports/allure_results/*.json
  ├─ 测试结果、步骤、参数、附件
  └─ environment.properties（env/base_url/browser/headless/python）
        │
        ▼
generate_report.py 读取 JSON
  → 汇总卡片 / 筛选 / 步骤树 / 失败截图 / GIF / 参数化数据
  → reports/html-report/index.html
```
