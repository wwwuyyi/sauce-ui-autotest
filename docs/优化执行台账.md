## T2 并发自证（临时脚本，未入库）

场景：FakeDriver 每 1ms 返回同一张 PNG；录制线程 `interval=0.005 / max_frames=20` 持续 append；主线程攒够 2 帧后连续 `save_gif` 300 次，统计成功次数与 `deque mutated during iteration` 日志。

| 版本 | 结果 |
|------|------|
| 修复前 | `calls=300 ok=151 failed=149`，`iteration-error-logs=147`（`GIF 合成失败: deque mutated during iteration`） |
| 修复后 | `ok=300/300 mutated=0` |

论证：`_run` 的 append 与 `save_gif`/`frame_count` 的读取共用 `_frames_lock`；`save_gif` 在锁内 `list(self._frames)` 得到独立快照，后续 `Image.open`/缩放/保存全部迭代快照，后台线程无法再修改被迭代的容器。

**T1 ❌ 打回（F1：缺席型成功谓词的时序回归，未申报）**

- 现象：3 处"成功 = 元素消失"型谓词改写为 `not is_element_visible(..., timeout=0)`：
  `cart_page.py:98`（remove_item）、`cart_page.py:123`（click_checkout）、
  `inventory_page.py:324`（click_product_link）。而 `BasePage._wait()` 用
  `timeout or self.timeout` 解析参数——**显式 0 被解析为默认 10s**，元素不存在时
  （WebDriverWait 默认忽略 NoSuchElementException）单次探测要空转满 10s 才返回 False。
- 实证：`click_product_link` 成功路径耗时 **HEAD 10.15s vs 基线 0.04s**；
  `remove_from_cart` 成功 0.10s（可见型谓词，元素出现即返回，不受影响）。
  连带效应：这 3 个方法的 `js_timeout=5` 复核预算实际也被首个 10s 探测吃穿（名义 5s 实际 ~10s）。
  全量套件中 test_item/test_cart/test_checkout/test_e2e 均命中此类路径，预计累计拖慢数分钟。
- 根因定性：`_wait()` 对显式 0 的解析是 P0 前既有 quirk（menu/checkout 共 17 处可见型谓词同受
  其害，注释宣称的"即时探测"从未真正成立），T1 把它扩散到了 3 个热路径。语义对照表中
  "成功条件等价"逻辑上成立，但**成功路径时延**是未申报的行为偏差，按指令 §6.4 打回。
- 修复要求（追加 DoD，方案由执行端决断）：
  1. 二选一：(a) 根治 `_wait()`——仅 `timeout is None` 才回退默认值，显式 0 按 0 处理
     （WebDriverWait 超时 0 = 单次探测），同时兑现全部 20 处 `timeout=0` 的"即时探测"文档
     承诺；需 grep 复核 20 处调用点无一依赖旧 quirk 并在台账记录结论。
     (b) 仅改 3 处缺席型谓词为 `get_element_count_immediate(locator) == 0`（即时计数，天然无等待）。
  2. 修复后探针复验：`click_product_link` / `remove_item` / `click_checkout` 成功路径 ≤ 1s，
     数据写入台账（探针脚本不入库）。

  4. 本次时序偏差补进 T1 行偏差列——未申报偏差本身即是打回原因之一，修复时一并纠正申报纪律。
