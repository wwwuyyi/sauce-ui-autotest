# Sauce UI 自动化项目教学手册（二）：参数与数据流转

> 本册专攻薄弱项：**入参、出参、参数流转、数据传递、参数隔离**。
>
> 读法：不要背表格。每看到一行，先在脑子里回答「这个值从哪来、变成什么类型、交给谁、失败会怎样」。三遍之后，你会形成条件反射。

---

## 1. 学参数的「六问法」

任何一次函数/方法/接口/类实例调用，都按下面六问拆：

1. **谁调用谁？** —— 调用发生在哪一层，被调用者属于哪一层。
2. **需要哪些入参？** —— 参数个数、名字、顺序。
3. **每个参数是什么？** —— 类型、含义、**来源**（写死？配置？上一步返回值？fixture？命令行？环境变量？）。
4. **怎么传？** —— 位置 / 关键字 / 默认值 / `*args` / `**kwargs` / 回调 / fixture 注入。
5. **返回什么？** —— 出参类型、数据结构、是否可能为 `None`。
6. **返回值去哪？** —— 被谁接收、参与什么判断、进入下一层哪个环节。

再加两个工程问题：

7. **失败了怎么办？** —— 抛异常？返回 `None`？返回空列表？重试？截图？
8. **参数能不能省？** —— 默认值是什么？能不能被覆盖？覆盖优先级是什么？

> 面试时，能把这八问答完整，就已经超过大多数「只会调方法」的候选人。

## 2. Python 传参的 8 种形式（全部能在项目里找到）

### 2.1 位置参数（positional）

```python
login_page.login("standard_user", "secret_sauce")
#                ^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^
#                第 1 个位置       第 2 个位置
```

对应定义：

```python
def login(self, username: str, password: str) -> None:
    ...
```

特点：

- 按顺序绑定，名字不重要；
- 参数少、语义明确时最简洁；
- 参数多且类型相同时容易写错顺序。

**项目里的例子**：

- `login_page.login(username, password)`
- `inventory_page.add_to_cart(slug)`
- `page.fill_info(first, last, zip_code)` ← 三个都是 `str`，顺序最容易错，读代码时要特别小心
- `find_element(locator, timeout)`

### 2.2 关键字参数（keyword）

```python
inventory_page.open_cart(fallback_url=CONFIG["urls"]["cart"])
#                          ^^^^^^^^^^^^ 明确告诉读代码的人：这是兜底 URL
```

对应定义：

```python
def open_cart(self, retries: int = 1, fallback_url: Optional[str] = None) -> None:
    ...
```

特点：

- 按名字绑定，顺序无关；
- 可读性强，尤其是布尔参数和可选参数；
- 只传一部分，其余走默认值。

**项目里的例子**：

- `open_cart(fallback_url=...)`
- `wait_buttons_reset(expected_add_count, timeout=...)`
- `click_product_link(product_id, retries=1)`
- `LoginPage(driver, timeout=..., poll_frequency=...)`
- `attachments` 里的 `name=...`, `attachment_type=...`

### 2.3 默认参数（default）

```python
def add_to_cart(self, slug: str, retries: int = 1) -> None:
    ...
```

调用方可以：

```python
inventory_page.add_to_cart("sauce-labs-backpack")          # retries 用默认 1
inventory_page.add_to_cart("sauce-labs-backpack", retries=0)  # 显式覆盖
```

**默认参数的价值**：80% 的调用不需要关心重试次数，只有特殊场景（如购物车删除）才显式传 0。

**默认参数的坑**：默认值在**函数定义时**求值一次。如果默认值是可变对象：

```python
def f(items=[]):      # 错误：所有调用共享同一个 list
    items.append(1)
```

项目里没有可变默认值，但面试常问。正确写法是 `items=None`，函数内再 `items = items or []`。

### 2.4 可变位置参数 `*args`

```python
def execute_script(self, script: str, *args):
    return self.driver.execute_script(script, *args)
```

调用：

```python
self.execute_script("arguments[0].click();", element)
# script = "arguments[0].click();"
# args   = (element,)
```

特点：

- `args` 是一个 **tuple**；
- 用来透传数量不定的位置参数；
- 再 `*args` 解包传给下一层。

**项目里的另一个例子**：

```python
return self.driver.find_elements(*locator)
# locator = (By.CSS_SELECTOR, ".inventory_item")
# 解包后等价于 find_elements(By.CSS_SELECTOR, ".inventory_item")
```

### 2.5 可变关键字参数 `**kwargs`

```python
def _create(page_class, **kwargs):
    return page_class(
        driver,
        timeout=config["timeout"]["explicit_wait"],
        poll_frequency=config["timeout"]["poll_frequency"],
        **kwargs
    )
```

调用：

```python
page_factory(InventoryPage)
page_factory(SomePage, custom_arg=123)
```

特点：

- `kwargs` 是一个 **dict**；
- 用来接收「工厂不关心、但页面类可能需要」的额外参数；
- 再 `**kwargs` 转发，保证工厂不需要随着页面构造参数变化而修改。

### 2.6 仅关键字参数（keyword-only）

Python 3 支持：

```python
def f(a, *, b):
    ...
f(1, b=2)   # 合法
f(1, 2)     # 报错
```

项目没有显式使用 `*`，但大量方法把可选参数放在后面，并鼓励用关键字传，达到类似效果。

### 2.7 回调函数作为参数（高阶函数）

```python
def click_robust(self, locator, success: Callable[[], bool], ...):
    ...
    if self._poll_success(success, timeout):
        return
```

调用：

```python
self.click_robust(
    self.add_button(slug),
    lambda: self.is_element_visible(self.remove_button(slug), timeout=0),
)
```

`success` 不是数据，而是**行为**：基础层调用它来判断「点击有没有生效」。这类参数叫**策略参数 / 回调参数**。

**项目里的回调参数清单**：

| 参数 | 类型 | 作用 |
| --- | --- | --- |
| `success` | `Callable[[], bool]` | 主成功条件 |
| `post_js_recheck` | `Optional[Callable[[], bool]]` | JS 点击后的页面级复核 |
| `retry_allowed` | `Optional[Callable[[], bool]]` | 是否允许重试 |
| `before_retry` | `Optional[Callable[[], None]]` | 重试前准备 |
| `on_final_failure` | `Optional[Callable[[], Optional[bool]]]` | 最终兜底，返回 True 表示已接管 |

**为什么用回调而不是在 BasePage 里写 if/else？**

- BasePage 不能知道「加购成功」和「退出成功」的定义；
- 用回调把业务判断留在页面层，基础层只负责通用流程；
- 新增页面不需要改 BasePage。

### 2.8 类作为参数

```python
def _create(page_class, **kwargs):
    return page_class(driver, ...)
```

调用：

```python
page_factory(InventoryPage)
page_factory(CartPage)
```

`page_class` 是一个**类对象**，不是实例。Python 里类也是可调用对象，调用它就会构造实例。

### 2.9 fixture 名作为参数（pytest 特有）

```python
def test_login_success_standard_user(self, login_page):
    ...
```

`login_page` 不是普通 Python 参数，而是 pytest 的**依赖注入声明**：

- pytest 扫描测试函数签名；
- 发现参数名 `login_page`；
- 去 fixture 注册表查找同名 fixture；
- 执行 fixture，把返回值注入；
- 同一测试内缓存，不重复执行。

**这不是「函数调用」，是「声明我需要什么」。** 面试时要区分清楚。

### 2.10 `parametrize` 的参数名

```python
@pytest.mark.parametrize("case_data", CONFIG["login_cases"]["required_field_cases"])
def test_login_required_field_validation(self, login_page, case_data):
    ...
```

`"case_data"` 是**字符串形式的参数名**，pytest 在收集阶段把每一组数据绑定到这个形参上，生成独立测试。

## 3. 入参来源判定：六种来源与识别方法

| 来源 | 识别特征 | 项目例子 | 生命周期 |
| --- | --- | --- | --- |
| 代码常量 | 全大写、类属性、`By.XXX` | `USERNAME_INPUT`、`MENU_TIMEOUT` | 进程 |
| 配置文件 | `CONFIG[...]`、`get_effective_config()` | 账号、URL、期望值 | 进程（每次读取深拷贝） |
| 上一步返回值 | 变量接收方法返回值再传下去 | `get_product(4)["slug"]` | 当前用例 |
| fixture | 测试函数参数、fixture 参数 | `driver`、`config`、`login_page` | fixture 作用域 |
| 命令行 | `request.config.getoption` | `--browser` | 本次运行 |
| 环境变量 | `os.environ.get` | `BASE_URL`、`HEADLESS` | 进程 |
| 参数化 | `parametrize` 的第二个参数 | `case_data`、`internal_path` | 收集阶段生成 |

**追踪一个参数来源的实操方法**：

1. 看调用点的实参：是字面量、变量、还是表达式？
2. 变量赋值处：是 `CONFIG[...]`、方法返回值、还是函数参数？
3. 函数参数：往上看谁调用它，继续追。
4. 追到 fixture / YAML / 命令行 / 环境变量，就是源头。

例：

```
inventory_page.add_to_cart(slug)
  ← slug = backpack["slug"]
  ← backpack = get_product(4)
  ← get_product 内部 CONFIG["products"] 中 id == 4 的条目
  ← CONFIG = get_effective_config()
  ← YamlUtil().read_yaml(CONFIG_PATH)
  ← config/env.yaml 的 products 列表
```

## 4. 核心方法参数总表

> 这张表建议打印出来。每一行都按「入参 → 出参 → 流向」理解。

### 4.1 工具层

| 方法 | 入参（类型 / 含义 / 来源） | 传参方式 | 出参 | 流向 / 副作用 |

| `_apply_wait_timeout(config)` | `config: dict`；来源：`get_effective_config` 内部 | 位置 | `None` | 原地修改 `timeout.explicit_wait` |
| `_apply_base_url(config)` | `config: dict`；同上 | 位置 | `None` | 原地修改 `base_url` 与 `urls.*` |
| `is_headless(browser_conf)` | `browser_conf: dict`；来源：`config["browser"]` | 位置 | `bool` | 被 `driver` fixture 用于决定是否加 `--headless` |
| `is_recording_enabled(recording_conf)` | `recording_conf: dict`；来源：`config["recording"]` | 位置 | `bool` | 被 `driver` fixture 用于决定是否启动录屏线程 |
| `get_edge_driver_path()` | 无 | - | `str`（空串表示自动管理） | 被 `driver` fixture 使用 |
| `get_product(product_id)` | `product_id: int`；来源：用例字面量（4/0/1/2/3/5） | 位置 | `dict`（slug/id/name/price） | 被用例拆出 `slug/name/price`，进入定位器和断言 |
| `set_severity_from_str(level)` | `level: str`；来源：`case_data["severity"]` 或字面量 | 位置 | `None` | 副作用：设置当前 Allure 用例严重级别 |
| `attach_text(content, name="附件")` | `content: str`；`name: str` 默认值 | 位置/关键字 | `None` | 副作用：写 Allure 文本附件 |

### 4.2 基础层

| 方法 | 入参 | 传参方式 | 出参 | 流向 / 失败行为 |
| --- | --- | --- | --- | --- |
| `BasePage.__init__(driver, timeout, poll_frequency)` | `driver: WebDriver`（fixture）；`timeout: int`（config）；`poll_frequency: float`（config） | 位置 + 关键字 | 实例 | 被页面类继承；`self.driver/timeout/poll_frequency` |
| `_wait(timeout=None)` | `timeout: Optional[int]`；`None`=实例默认，`0`=单次探测 | 位置 | `WebDriverWait` | 被所有 `find_*` / `wait_*` 使用 |

| `find_elements(locator, timeout=None)` | 同上 | 位置 | `List[WebElement]` | 被列表读取方法使用；**零元素会超时**，零计数场景改用 `get_element_count_immediate` |
| `find_element_presence(locator, timeout=None)` | 同上 | 位置 | `WebElement` | 用于隐藏元素属性读取（如 `.bm-menu-wrap` 的 aria-hidden） |
| `find_element_clickable(locator, timeout=None)` | 同上 | 位置 | `WebElement` | 点击前等待可点击 |
| `click(locator, timeout=None)` | 同上 | 位置 | `None` | 副作用点击；失败截图 + 抛异常 |
| `input_text(locator, text, clear_first=True)` | `text: str`（账号/表单值）；`clear_first: bool` | 位置 + 关键字 | `None` | 副作用输入；失败截图 + `ValueError` |
| `get_text(locator, timeout=None)` | locator；timeout | 位置 | `str` | 被断言使用；失败抛异常 |
| `get_attribute(locator, attribute, timeout=None)` | `attribute: str`（如 `"value"`/`"aria-hidden"`） | 位置 | `Optional[str]` | 被 `get_username_value` / 菜单状态读取使用 |
| `execute_script(script, *args)` | `script: str`；`*args` 任意 JS 参数 | 位置 + 可变 | JS 返回值 | 被 `js_click`、JS 写值、诊断使用 |
| `js_click(locator, timeout=None)` | locator | 位置 | `None` | 原生点击兜底 |
| `click_robust(locator, success, timeout=10, js_timeout=5, retries=1, fail_message=..., post_js_recheck=None, retry_allowed=None, before_retry=None, on_final_failure=None)` | 1 个定位器 + 5 个回调 + 4 个数值/字符串参数 | 位置 + 关键字 | `None` | 失败抛 `TimeoutException`；页面层通过关键字传回调 |
| `click_until(locator, success, timeout=10, js_timeout=5, retries=1, fail_message=...)` | 同上（无页面钩子） | 位置 + 关键字 | `None` | 委托 `click_robust` |
| `wait_until(condition, timeout=None, fail_message=...)` | `condition: Callable[[WebDriver], bool]`（接收 driver） | 位置 + 关键字 | `None` | 自定义等待；超时抛异常 |
| `wait_text_equals(locator, text, timeout=None)` | `text: str` 期望文本 | 位置 | `None` | 角标精确等待，避免 `'1'` 匹配 `'12'` |
| `get_element_count_immediate(locator)` | locator | 位置 | `int` | 零计数断言（购物车清空、角标消失） |
| `save_screenshot(name="screenshot")` | `name: str` 前缀 | 位置 | `str` 绝对路径 | 截图落盘，不参与断言 |

### 4.4 fixture 与用例层

| fixture / 函数 | 入参 | 出参 | 关键点 |
| --- | --- | --- | --- |
| `config()` | 无 | `dict` | function 级，每次深拷贝 |
| `driver(request, config)` | `request`（pytest 内置）、`config` | `WebDriver`（yield） | teardown 关闭 driver；失败钩子从 `funcargs` 取 |
| `login_page(driver, config)` | driver/config | `LoginPage` | 已打开 base_url；注入等待策略 |
| `page_factory(driver, config)` | driver/config | `_create` 函数 | 闭包捕获 driver/config；`**kwargs` 转发 |
| `inventory_page(login_page, page_factory, config)` | 三个 fixture | `InventoryPage` | 真实 UI 登录 standard 账号 |
| `cart_page(inventory_page, page_factory, config)` | 三个 fixture | `CartPage` | 预置 2 件商品并进购物车 |
| `checkout_step_one_page(cart_page, page_factory, config)` | 三个 fixture | `CheckoutPage` | 点击 Checkout；超时则 URL 直达 |
| `checkout_overview_page(checkout_step_one_page, config)` | 前一步 + config | 同一个 `CheckoutPage` | 填 `valid_info` 并提交 |
| `test_xxx(login_page, case_data)` | fixture + 参数化 dict | `None`（靠 assert） | 参数名即契约 |

## 5. 出参结构与数据流向

### 5.1 出参类型目录

| 出参类型 | 项目例子 | 典型用途 |
| --- | --- | --- |
| `None` | `login()`、`click()`、`add_to_cart()` | 动作类：靠副作用改变页面状态 |
| `bool` | `is_element_visible()`、`is_badge_absent()`、`open_about_and_navigate()` | 条件判断 / 分支 |
| `str` | `get_text()`、`get_current_url()`、`get_badge_text()` | 断言文本/URL |
| `int` | `get_product_count()`、`get_add_button_count()` | 数量断言 |
| `float` | `login_and_measure_inventory_load()` | 性能阈值比较 |
| `list` | `get_product_names()`、`get_product_prices()` | 序列比较 |
| `dict` | `get_summary_label_texts()`、`get_summary_amounts()`、`get_product(id)` | 结构化数据，按键取值 |
| `WebElement` | `find_element()`、`find_element_clickable()` | 底层操作对象，通常不跨层返回 |
| 页面对象 | fixture 返回值、`page_factory(...)` | 供用例调用业务方法 |
| 函数 | `page_factory` 的出参 `_create` | 工厂/延迟创建 |
| `Decimal` | `get_price_numbers()`、`get_summary_amounts()` | 金额精确计算 |
| 异常 | `TimeoutException` / `ValueError` | 失败路径 |

### 5.2 链路一：商品 id → 定位器 → 页面状态 → 断言

```
CONFIG["products"] 是 list[dict]
        │
        │ get_product(4)
        ▼
{"slug": "sauce-labs-backpack", "id": 4, "name": "Sauce Labs Backpack", "price": "29.99"}
        │
        ├─ ["slug"] ──► add_button(slug) ──► (By.CSS_SELECTOR, "[data-test='add-to-cart-sauce-labs-backpack']")
        │                                              │
        │                                              ▼
        │                                       click(locator)
        │                                              │
        │                                              ▼
        │                                   Remove 按钮出现 / 角标变为 "1"
        │
        ├─ ["name"] ──► 购物车名称断言
        └─ ["price"] ─► f"${price}" 价格断言
```

**类型变化**：`int` → `dict` → `str` → `tuple` → `WebElement` → 页面状态 → `str/int`（读取）→ `bool`（assert）。

### 5.3 链路二：fixture 链把「前置状态」变成「对象」

```
config fixture (dict)
  │
  ├─ driver fixture ──► WebDriver
  │       │
  │       ▼
  │   login_page fixture ──► LoginPage(driver, timeout=10, poll_frequency=0.5)
  │       │                     │
  │       │                     └─ open_url(config["base_url"])
  │       ▼
  │   login_page.login_and_wait_inventory(username, password)
  │       │
  │       ▼
  │   页面跳转到 inventory
  │       │
  │       ▼
  │   inventory_page fixture ──► page_factory(InventoryPage) ──► InventoryPage(driver, ...)
  │                                                              │
  │                                                              └─ wait_inventory_loaded()
  │       ▼
  │   cart_page fixture ──► add_items_to_cart(["sauce-labs-backpack","sauce-labs-bike-light"])
  │                     ──► open_cart(fallback_url=...)
  │                     ──► page_factory(CartPage) ──► CartPage(driver, ...)
  │       ▼
  │   用例：cart_page.get_cart_item_names()
```

**关键点**：每个 fixture 的**出参**是下一层 fixture 的**入参**。这就是「fixture 链式传参」。

### 5.4 链路三：页面 dict → Decimal → 断言

```
CheckoutPage.get_summary_label_texts()
  → {"subtotal": "Item total: $39.98",
     "tax": "Tax: $3.20",
     "total": "Total: $43.18"}
        │
        │ get_summary_amounts() 内部：
        │   {key: Decimal(text.split("$")[-1]) for key, text in labels.items()}
        ▼
{"subtotal": Decimal("39.98"),
 "tax": Decimal("3.20"),
 "total": Decimal("43.18")}
        │
        ├─ 期望 subtotal = Decimal("29.99") + Decimal("9.99")
        ├─ 期望 tax = (subtotal * Decimal("0.08")).quantize(...)
        └─ 断言 amounts["total"] == subtotal + tax
```

**为什么用 Decimal 不用 float？**

`0.1 + 0.2 != 0.3` 在二进制浮点里成立。金额断言必须精确到分，所以从字符串直接构造 `Decimal`，并用 `ROUND_HALF_UP` 明确舍入规则。

### 5.5 链路四：parametrize 数据 → 方法入参 → 期望值

```
YAML login_cases.required_field_cases
  → list[dict]
        │ pytest 收集阶段，每个 dict 生成一条测试
        ▼
case_data = {
  "case_id": "SAUCE-LOGIN-004",
  "username": "",
  "password": "",
  "expected_error": "username_required",
  "severity": "critical",
}
        │
        ├─ case_data["username"] / ["password"] → login_page.login(username, password)
        ├─ case_data["expected_error"] → CONFIG["expected"]["error_messages"][key] → 期望文案
        └─ case_data["severity"] → set_severity_from_str(level)
```

**注意**：`expected_error` 存的是**键名**，不是文案本身；文案在 `expected.error_messages` 里。这是「数据引用数据」的解耦设计：文案集中一处，改文案不用改多组用例。

### 5.6 链路五：yield 生命周期

```python
@pytest.fixture
def driver(...):
    driver_obj = webdriver.Chrome(...)   # setup
    yield driver_obj                      # 把出参交给用例
    driver_obj.quit()                     # teardown
```

- `yield` 之前：setup；
- `yield` 的值：fixture 的出参；
- `yield` 之后：teardown，无论用例成功/失败都执行（除非进程被杀）；
- 如果 setup 抛异常，teardown 不执行。

### 5.7 链路六：旁路上下文（request.node → hook）

```
driver fixture:
    request.node._screen_recorder = recorder
                    │
                    │ 不是函数参数，挂在 pytest 节点对象上
                    ▼
pytest_runtest_makereport(item, call):
    recorder = getattr(item, "_screen_recorder", None)
    recorder.save_gif(...)
```

这是「没有直接调用关系」的数据传递：fixture 和 hook 都拿得到 `item` 节点，通过节点属性交换对象。

## 6. 跨用例共享数据：五种方案与面试答法

先给结论：**本项目刻意不让用例之间共享运行时数据**。用例之间只共享「只读的配置基线」，不共享「登录态、购物车、页面对象」。

### 6.1 方案对比

| 方案 | 存储位置 | 生命周期 | 适合 | 优点 | 缺点 | 项目例子 |
| --- | --- | --- | --- | --- | --- | --- |
| ① fixture 返回值链 | pytest fixture 缓存 | 单条用例 | 同一用例内的前置状态 | 显式依赖、自动 teardown、隔离好 | 不能跨用例 | `driver → login_page → inventory_page → cart_page` |
| ② 模块级只读配置 | Python 模块全局变量 | 进程 | 静态基线数据 | 简单、读取快 | 可变对象有污染风险；不随用例重置 | `CONFIG = get_effective_config()` |
| ③ `parametrize` | pytest 收集参数 | 收集阶段 → 每条测试 | 输入矩阵 | 一条数据一条报告、失败隔离 | 只适合静态数据，不能传运行期结果 | `case_data`、`internal_path` |
| ④ 命令行 / 环境变量 | 进程环境 | 本次运行 | 环境切换、CI 配置 | 不改代码、优先级高 | 类型都是字符串，要转换；难表达复杂结构 | `--browser`、`BASE_URL` |
| ⑤ session fixture / 全局变量 / 文件 | 进程内存 / 磁盘 | 跨用例/跨进程 | 真正的跨用例状态 | 可复用、快 | 顺序依赖、并行冲突、清理复杂、易污染 | 本项目**不用** |

### 6.2 为什么本项目不用「登录一次，所有用例共享」

- 每条用例独立 driver（function 级），登录态在浏览器里，不在 Python 内存里；
- 共享 driver 会让用例顺序影响结果：A 用例清了购物车，B 用例就失败；
- xdist 并行时多个 worker 是不同进程，内存变量根本共享不了；
- 项目选择「每条用例重新真实登录」，用时间换确定性。

### 6.3 如果面试官追问「那怎么优化登录耗时？」

可以这样答（分三层）：

1. **保留隔离，优化登录动作**：登录接口/页面操作本身很快，真正慢的是浏览器启动；可以用 session 级 driver + 每条用例重置 localStorage/cookie，但必须保证状态清理。
2. **用 storage_state / cookie 注入**：登录一次保存 cookie，后续用例注入。但本项目明确「正式用例一律真实 UI 登录，禁止 cookie 注入式登录」，因为要覆盖登录链路本身，且注入会绕过 UI 风险。
3. **并行**：xdist 多 worker，每条用例独立 driver，用并行抵消单条启动成本。项目全量记录约 1 分 32 秒（16 worker）。

### 6.4 如果确实要跨用例传数据，怎么设计？

给出「最小可用」方案：

```python
# conftest.py
@pytest.fixture(scope="session")
def shared_data():
    return {}          # 一个显式的共享字典

# 用例 A
def test_create(shared_data):
    shared_data["order_id"] = create_order()

# 用例 B（必须依赖 A 先执行）
def test_query(shared_data):
    order_id = shared_data["order_id"]
```

但要说明代价：

- 引入顺序依赖，不能单独运行 B；
- 并行时不同进程不共享；
- 测试失败后残留数据影响后续；
- 需要显式的清理和唯一 ID。

更推荐的做法：**每条用例自己创建自己需要的数据**（API 造数最快），把「共享」变成「独立准备」。

### 6.5 面试标准回答（背这段）

> 我们的用例之间不共享运行时数据，只共享只读配置。配置放在 YAML，读取时深拷贝，每个用例拿到独立副本。同一条用例内部的前置状态用 fixture 返回值链传递，比如 driver → login_page → inventory_page → cart_page；参数化数据用 parametrize 在收集阶段展开，每组数据一条独立用例。这样做的好处是用例可以单独运行、可以并行、失败不互相污染。代价是每条用例都要重新登录，我们用 function 级 driver 加 xdist 并行来平衡速度和隔离。

## 7. 参数隔离：七个层次

| 隔离点 | 机制 | 代码位置 | 如果不做会怎样 |
| --- | --- | --- | --- |
| 浏览器 | function 级 driver，每条用例新建/退出 | `conftest.py` `driver` | Cookie/购物车/登录态串味 |
| 配置 | `read_yaml` 深拷贝 + `config` fixture 每次读 | `yaml_util.py` / `conftest.py` | 一个用例改配置影响全部 |
| YAML 缓存 | 缓存原对象，返回 `deepcopy` | `yaml_util.py` | 调用方改返回值污染缓存 |
| 用例输入 | `parametrize` 每条独立 test item | 测试文件 | 一条失败中断整组 |
| 页面对象 | 每个 fixture 新建页面对象，但共享同一 driver | `page_factory` | 页面对象持有过期元素 |
| 进程 | xdist 每 worker 独立进程 | CI/命令行 | 全局变量跨 worker 不共享 |
| 失败产物 | 截图按用例名 + 时间戳命名 | `conftest.py` | 文件互相覆盖 |

**注意一个细节**：`get_product()` 直接返回 `CONFIG["products"]` 里的 dict，没有深拷贝。`CONFIG` 本身是 `get_effective_config()` 的副本，但它是**模块级**的，同模块所有用例共享。如果某个用例修改了 `get_product(4)` 返回的 dict，会影响同模块后续用例。项目里所有用例只读，所以没问题；但面试问「你的数据隔离有没有漏洞」时，要能指出这一点，并给出修复方案（返回 `copy.deepcopy(product)`）。

## 8. 参数覆盖与优先级

### 8.1 完整优先级表

| 参数 | 第一优先 | 第二优先 | 第三优先 | 代码位置 |
| --- | --- | --- | --- | --- |
| 浏览器 | `--browser` 命令行 | `env.yaml` `browser.name` | 默认 chrome | `pytest_addoption` + `driver` |
| 测试地址 | `BASE_URL` 环境变量 | `env.yaml` `base_url` | 无 | `_apply_base_url` |
| 显式等待 | `WAIT_TIMEOUT` 环境变量 | CI 环境默认 30s | `env.yaml` `timeout.explicit_wait` | `_apply_wait_timeout` |
| 无头 | `HEADLESS` 环境变量 | `env.yaml` `browser.headless` | false | `is_headless` |
| 录屏 | `RECORDING=false` | `env.yaml` `recording.enabled` | true | `is_recording_enabled` |
| Edge 驱动 | `EDGE_DRIVER_PATH` | Selenium Manager | - | `get_edge_driver_path` |
| 单次等待 | 方法 `timeout=` 显式传入 | 实例 `self.timeout` | 类默认 10 | `_wait` |
| 输入清空 | 方法 `clear_first=` | 默认 True | - | `input_text` |
| 点击重试 | 方法 `retries=` | 默认 1 | - | `click_robust` |
| 用例数据 | `parametrize` 数据组 | 无 | - | 测试文件 |

### 8.2 一个容易错的细节：`or` vs `is None`

项目里 `_wait` 已经修成：

```python
wait_timeout = self.timeout if timeout is None else timeout
```

但 `sort_and_wait_names` 里还有：

```python
base_timeout = timeout or self.timeout
```

如果调用方传 `timeout=0`，这里会回退成 `self.timeout`，与 `_wait` 的语义不一致。面试如果问「你的参数默认值有没有坑」，可以主动指出这类不一致，说明你知道 `0` 是合法值。

### 8.3 环境变量的类型转换

环境变量永远是字符串：

```python
wait_timeout_env = (os.environ.get("WAIT_TIMEOUT") or "").strip()
if wait_timeout_env.isdigit():
    config["timeout"]["explicit_wait"] = int(wait_timeout_env)
```

- 先判空，再判 `isdigit()`，最后 `int()`；
- 如果直接 `int(os.environ.get(...))`，未设置时会 `TypeError`；
- 布尔值要显式比较 `== "true"`，不能直接 `bool("false")`（非空字符串都是 True）。

## 9. 参数坑点清单（面试高频）

### 坑 1：`None`、`""`、`0` 含义不同

- `None`：没有值 / 未提供；
- `""`：提供了空字符串，在项目里表示「这个字段不输入」；
- `0`：合法的数值，比如 `timeout=0` 表示单次探测。

项目里：

```python
login_cases.required_field_cases[0].username = ""   # 空字符串，不是 None
```

如果把它改成 `None`，`input_text` 里的 `send_keys(None)` 会出问题。

**答法**：默认值参数用 `None` 做哨兵；业务上的「空输入」用 `""`；数值型的 0 不要用 `or` 兜底。

### 坑 2：位置参数顺序写错

```python
page.fill_info(first, last, zip_code)
```

三个都是 `str`，如果写成 `fill_info(last, first, zip)`，Python 不会报错，但断言会失败。

**防御**：

- 参数多且类型相同，调用时用关键字：`fill_info(first=..., last=..., zip_code=...)`；
- 或者把参数收成一个 dict（如 `info`），但会增加解包成本；
- 代码评审时重点看这种「同类型多参数」。

### 坑 3：`*locator` 忘记解包

```python
driver.find_elements(locator)      # 错误：只传了一个 tuple
driver.find_elements(*locator)     # 正确：解包成 by, value
```

### 坑 4：`staticmethod` 绑定

```python
remove_button = staticmethod(InventoryPage.remove_button)   # 正确
remove_button = InventoryPage.remove_button                 # 错误：调用时多传 self
```

### 坑 5：闭包晚绑定

```python
for slug in slugs:
    callbacks.append(lambda: page.add_to_cart(slug))
# 所有 lambda 都捕获同一个 slug 变量，循环结束后都是最后一个
```

项目里的 lambda 都在单次方法调用内捕获参数，不存在循环晚绑定；但面试可能问，答「用默认参数 `lambda s=slug: ...` 或 `functools.partial` 绑定当前值」。

### 坑 6：`parametrize` 的 `ids` 长度不匹配

```python
@pytest.mark.parametrize("case_data", cases, ids=[...])
```

`ids` 的长度必须等于 `cases` 的长度，否则 pytest 报错。项目的 `ids` 都用列表推导从同一份数据生成，天然一致。

### 坑 7：fixture 名字写错

```python
def test_x(login_pages):   # 少一个 s
```

pytest 报 `fixture 'login_pages' not found`。不是 Python 的 `NameError`，而是 pytest 的 fixture 解析错误。要区分。

### 坑 8：fixture 作用域不匹配

session 级 fixture 不能依赖 function 级 fixture。例如：

```python
@pytest.fixture(scope="session")
def shared(config):   # config 是 function 级 → ScopeMismatch
```

项目的 fixture 全是 function 级，所以不存在；但如果要优化，必须注意这条规则。

### 坑 9：共享可变数据

- `parametrize` 的每组 dict 是同一个对象，用例内修改会影响同组数据（如果被复用）；
- 模块级 `CONFIG` 是共享的；
- `get_product` 返回的 dict 是共享的。

**防御**：只读；需要修改时先深拷贝。

### 坑 10：动作方法返回 `None`，却链式调用

```python
page.login(...).get_current_url()   # AttributeError: 'NoneType'
```

动作方法的设计就是返回 `None`，不要链式调用。

### 坑 11：`get_cookie` 可能返回 `None`

```python
cookie = login_page.get_cookie("session-username")
assert cookie is not None
assert cookie["value"] == ...
```

先判空再下标，否则 `TypeError`。

### 坑 12：零元素不能用 `find_elements`

`find_elements` 内部先等 `presence_of_all_elements_located`，元素数为 0 时会一直等到超时。项目用 `get_element_count_immediate` 处理「期望 0 个」的场景。

### 坑 13：页面重渲染导致元素失效

`StaleElementReferenceException`：拿到元素后页面刷新，元素句柄失效。项目在 `input_text` 里捕获它并重新定位；一般原则是「不要长期持有 WebElement，操作前重新查找」。

### 坑 14：环境变量是字符串

`HEADLESS=false` 不能直接 `bool(...)`；`WAIT_TIMEOUT=20` 要 `int()`；`BASE_URL` 要处理结尾斜杠。

### 坑 15：敏感信息进日志

`input_text` 的日志只记录 locator，不记录 text；密码不会落盘。面试问「密码怎么管理」时，答「YAML 占位 + CI Secrets / 环境变量覆盖，日志不回显」。

### 坑 16：相对路径

`open("config/env.yaml")` 依赖当前工作目录；项目用 `PROJECT_ROOT / path` 统一解析。

## 10. fixture 传参深度

### 10.1 作用域（scope）

| scope | 生命周期 | 项目是否使用 | 适用 |
| --- | --- | --- | --- |
| `function` | 每条测试 | ✅ 全部 | 需要隔离的浏览器、页面对象 |
| `class` | 每个测试类 | ❌ | 类内共享 |
| `module` | 每个模块 | ❌ | 模块级只读资源 |
| `package` | 每个包 | ❌ | 包级资源 |
| `session` | 整个运行 | ❌ | 全局配置、数据库连接 |

### 10.2 依赖注入与缓存

```python
@pytest.fixture
def inventory_page(login_page, page_factory, config):
    ...
```

- pytest 先解析 `login_page`、`page_factory`、`config`；
- 如果同一测试里另一个 fixture 也请求 `login_page`，pytest 复用同一个实例（function 作用域内缓存）；
- 这就是为什么 `test_logout(self, inventory_page, page_factory, login_page)` 里的 `login_page` 和 `inventory_page` 内部用的是同一个 LoginPage 实例。

### 10.3 `yield` 与 teardown 顺序

```
setup: config → driver → login_page → inventory_page → cart_page
call:  test
teardown: cart_page → inventory_page → login_page → driver（反向）
```

`driver` 的 teardown 最后执行，先停录屏再 `quit()`，避免对已关闭会话截图。

### 10.4 参数化的 fixture（项目未用，但面试会问）

```python
@pytest.fixture(params=["chrome", "firefox"])
def browser(request):
    return request.param
```

这会让每条测试在每个参数上各跑一次。本项目用命令行 `--browser` 切换，而不是 fixture params，因为浏览器切换是「本次运行的选择」，不是「每条用例的矩阵」。

### 10.5 `autouse`（项目未用）

```python
@pytest.fixture(autouse=True)
def setup_log():
    ...
```

自动作用于每个测试。项目只在 `conftest.py` 模块级调用 `LogUtil.setup()`，没有用 autouse，避免隐式依赖。

### 10.6 `request.getfixturevalue`（项目未用）

动态获取 fixture：

```python
def test_x(request):
    page = request.getfixturevalue("login_page")
```

适合「参数决定用哪个 fixture」的场景；项目的 `page_factory` 用普通函数替代了这种动态性。

### 10.7 fixture vs 普通函数

| 维度 | fixture | 普通函数 |
| --- | --- | --- |
| 调用方式 | 测试参数名注入 | 显式调用 |
| 生命周期 | pytest 管理 setup/teardown | 调用方管理 |
| 缓存 | 同一测试内复用 | 每次调用新建 |
| 作用域 | 可配置 | 无 |
| 适合 | 前置状态、资源 | 纯计算、工具 |

## 11. 面试 30 问（参数专项）

> 每题给「一句话答案 + 可展开点」。面试时先说结论，再展开。

1. **你的测试数据放在哪？**
   `config/env.yaml`，地址、浏览器、账号、期望值、参数化用例数据全部外置；代码零硬编码。

2. **YAML 怎么读？**
   `YamlUtil` 单例 + 文件缓存 + `safe_load` + 深拷贝；`config_util` 再做环境变量覆写。

3. **为什么读取要深拷贝？**
   防止调用方修改返回值污染缓存和其他用例；配置量小，深拷贝成本可忽略。

4. **环境变量和 YAML 谁优先？**
   环境变量优先（`BASE_URL`/`WAIT_TIMEOUT`/`HEADLESS`），命令行 `--browser` 覆盖浏览器；这样 CI 不用改仓库文件。

5. **命令行参数怎么注册？**
   `pytest_addoption` 注册 `--browser`，`request.config.getoption` 读取，默认值来自 YAML。

6. **fixture 怎么给用例传参？**
   测试函数参数名 = fixture 名，pytest 依赖注入；不是普通函数调用。

7. **fixture 作用域是什么？为什么？**
   function 级；每条用例独立浏览器，登录态/购物车/Cookie 不互相污染；用并行补速度。

8. **fixture 之间怎么传数据？**
   依赖声明 + 返回值：`inventory_page` 依赖 `login_page`，登录后返回新的 `InventoryPage`；`cart_page` 依赖 `inventory_page`，加购后返回 `CartPage`。

9. **用例之间共享数据吗？**
   不共享运行时数据，只共享只读配置；跨用例共享会引入顺序依赖和并行冲突。

10. **参数化怎么做？**
    `@pytest.mark.parametrize("case_data", list_of_dicts, ids=[...])`；一组数据一条独立测试。

11. **parametrize 在什么时候展开？**
    收集阶段；不是运行时循环。

12. **ids 有什么用？**
    报告/命令行可读；通常用业务用例编号。

13. **参数为空怎么办？**
    区分 `None` 和 `""`；项目用 `""` 表示不输入；`input_text` 用 `target = text or ""` 防御 None，但 `send_keys(None)` 仍可能出错，业务上不传 None。

14. **默认参数有什么坑？**
    可变默认值共享；用 `None` 做哨兵；`0`/`""` 是合法值时不要用 `or` 兜底。

15. **参数覆盖优先级怎么设计？**
    命令行 > 环境变量 > 配置文件 > 代码默认；方法级 `timeout` > 实例默认 > 类默认。

16. **动态定位器怎么传？**
    把 `slug` 传给 `add_button(slug)`，页面层用 f-string 拼 `data-test`；`slug` 来自 `get_product(id)["slug"]`。

17. **slug 从哪来？**
    YAML 商品表 → `get_product(id)` → dict → `["slug"]`。

18. **动作方法为什么返回 None？**
    副作用已经表达结果；返回元素会让用例耦合底层；成功与否通过「等待成功条件 + 异常」表达。

19. **读取方法返回什么结构？**
    文本 `str`、数量 `int`、列表 `list[str]`、金额 `dict[str, Decimal]`、条件 `bool`。

20. **`click_robust` 的参数为什么这么设计？**
    `locator` + 成功条件回调 + 各级超时/重试/兜底回调；BasePage 不知道业务成功定义，由页面层注入。

21. **`page_factory` 为什么返回函数？**
    工厂模式：闭包捕获 driver/config，按需创建任意页面；避免为每个页面写 fixture。

22. **`*args` / `**kwargs` 用在哪？**
    `execute_script(script, *args)` 透传 JS 参数；`_create(page_class, **kwargs)` 转发页面构造参数。

23. **位置参数和关键字参数怎么选？**
    参数少且语义明确用位置；参数多、类型相同、可选项多用关键字；布尔参数强烈建议关键字。

24. **参数隔离怎么做？**
    function driver + 配置深拷贝 + YAML 缓存深拷贝 + parametrize 独立 test item + xdist 多进程。

25. **并行时数据怎么共享？**
    不共享；每个 worker 独立进程、独立 driver；需要共享用外部存储（文件/DB），但要处理并发和清理。

26. **敏感信息怎么传？**
    YAML 占位 + 环境变量/CI Secrets 覆盖；日志不回显输入内容。

27. **失败截图怎么拿到 driver？**
    `pytest_runtest_makereport` 钩子里 `item.funcargs.get("driver")`，当前测试的 fixture 值。

28. **新增一组参数化数据要改代码吗？**
    不用；在 YAML 对应列表加一组 dict 即可。

29. **新增一个页面要改哪些参数？**
    新增 Page 类（定位器 + 业务方法），用例通过 `page_factory(NewPage)` 创建；base 和 fixture 不用改。

30. **你觉得这个项目参数设计最大的优点和缺点？**
    优点：分层收窄、数据外置、fixture 链显式、回调解耦；缺点：部分位置参数（`fill_info`）易错、模块级 CONFIG 共享可变 dict、`sort_and_wait_names` 的 `or` 与 `_wait` 语义不一致。
