## 模块一：登录（LOGIN）

### 1.1 业务链路

```
打开 base_url
  → 输入 username
  → 输入 password
  → 点击 login-button
  → 成功：跳转 /inventory.html，商品列表出现，写 session-username Cookie
  → 失败：停留登录页，h3[data-test='error'] 显示错误文案
```

### 1.2 直白版（不封装）

```python
def test_login(driver):
    driver.get("https://www.saucedemo.com/")
    driver.find_element(By.ID, "user-name").send_keys("standard_user")
    driver.find_element(By.ID, "password").send_keys("secret_sauce")
    driver.find_element(By.ID, "login-button").click()
    assert driver.current_url == "https://www.saucedemo.com/inventory.html"
```

**直白版的问题**：

- 没有等待，元素未渲染就查找；
- 没有失败截图；
- 账号、密码、URL 写死；
- 无法复用给锁定账号、错误账号、特殊账号；
- 用例既知道定位器，又知道业务，违反分层。

### 1.3 项目版：页面对象

```python
class LoginPage(BasePage):
    USERNAME_INPUT = (By.ID, "user-name")
    PASSWORD_INPUT = (By.ID, "password")
    LOGIN_BUTTON = (By.ID, "login-button")

    def input_username(self, username: str) -> None:
        # 【入参】username：str；来源：conftest 的 accounts.standard.username
        # 【出参】None；副作用：向 USERNAME_INPUT 输入
        self.input_text(self.USERNAME_INPUT, username)

    def input_password(self, password: str) -> None:
        # 【入参】password：str；来源：conftest 的 accounts.standard.password
        # 【出参】None；副作用：向 PASSWORD_INPUT 输入
        self.input_text(self.PASSWORD_INPUT, password)

    def click_login(self) -> None:
        # 【入参】无
        # 【出参】None；副作用：点击登录
        self.click(self.LOGIN_BUTTON)

    def login(self, username: str, password: str) -> None:
        # 【入参】username/password：两个 str，位置参数
        # 【出参】None；不判断成功失败，只负责提交
        logger.info("执行登录业务流: 用户名=%s", username)   # 密码不落日志
        self.input_username(username)
        self.input_password(password)
        self.click_login()
```

**为什么 `login` 不判断成功失败？**

- 页面对象的职责是「执行动作」，不是「决定测试结果」；
- 成功/失败由用例断言：成功用例等 inventory，失败用例读 error message；
- 同一个 `login()` 可以被正向、反向、特殊账号复用。

### 1.4 带重试的登录：`login_and_wait_inventory`

公共演示站偶发「凭证正确但被拒绝」，所以项目封装了带重试的版本：

```python
def login_and_wait_inventory(self, username: str, password: str,
                             timeout: Optional[int] = None, retries: int = 1) -> None:
    # 【入参】username/password：str，账号密码
    # 【入参】timeout：Optional[int]；None=使用实例默认 10s；慢账号传 config["timeout"]["glitch_wait"]=20
    # 【入参】retries：int；默认 1，即最多尝试 2 次
    # 【出参】None；成功时商品列表已加载
    for attempt in range(retries + 1):
        self.login(username, password)
        try:
            self.wait_inventory_loaded(timeout)   # 等列表出现
            return
        except TimeoutException as exc:
            error = self.get_error_message_or_empty()
            if not error:
                # 没有错误提示 = 纯加载超时，不是登录被拒，原样抛出
                raise
            if attempt < retries:
                logger.warning("登录被站点拒绝[%s]，自动重试 %d/%d", error, attempt + 1, retries)
                continue
            raise TimeoutException(f"登录被拒绝: {error}") from exc
```

**【参数相关注释】**

- `timeout` 默认 `None`：页面方法把「不传」解释为「用实例默认值」；慢账号显式传 20；
- `retries=1`：只重试一次，避免把确定性失败掩盖成偶发；
- **只有检测到错误文案才重试**：纯加载超时不重试，保持原始报错语义；
- 出参是 `None`，但副作用是「列表已加载」；调用方通过后续读取确认状态。

### 1.5 性能计时：`login_and_measure_inventory_load`

```python
def login_and_measure_inventory_load(self, username: str, password: str,
                                     timeout: Optional[int] = None) -> float:
    # 【入参】同上
    # 【出参】float：从点击登录到列表可见的秒数
    t0 = time.monotonic()          # 单调时钟，不受系统时间调整影响
    self.login(username, password)
    self.wait_inventory_loaded(timeout)
    elapsed = time.monotonic() - t0
    logger.info("登录到商品列表加载耗时: %.2f 秒", elapsed)
    return elapsed
```

**出参流向**：

```
elapsed: float
  ├─ 用例里 assert elapsed >= CONFIG["special_users"]["glitch_min_delay"]
  ├─ 基线比较 assert t_glitch >= 2 * t_base
  └─ allure.attach(str(round(elapsed, 2)), "实际加载耗时(秒)", ...)
```

### 1.9 【面试必背话术】

> 登录模块我做了三件事：第一，把三个定位器收口在 `LoginPage`，用例不碰 driver；第二，把登录流程封装成 `login(username, password)`，只负责提交，不负责判定成功失败，这样正向、反向、特殊账号都能复用；第三，针对公共站点偶发拒绝，加了 `login_and_wait_inventory`，只有检测到错误文案才重试，纯加载超时不重试，避免掩盖真实问题。数据全部来自 YAML，账号用 `accounts.standard` 这样的键读取，期望文案用 `expected.error_messages` 的键引用，改文案只改一处。

### 1.10 【面试官高频追问清单】

1. **账号密码从哪来？** YAML 的 `accounts`，用例读取 dict 后拆成两个位置参数。
2. **为什么不用 cookie 注入登录？** 登录链路本身要覆盖；注入会绕过 UI 风险，且项目约定正式用例必须真实 UI 登录。
3. **登录失败怎么判定？** 读 `h3[data-test='error']` 的文本，和 YAML 期望文案精确比较；同时断言仍停留在登录页、没有会话 Cookie。
4. **`timeout` 参数为什么单独抽出来？** glitch/error 账号渲染慢，默认 10s 不够，传 `glitch_wait=20`；普通账号走默认，避免每条用例都写超时。
5. **重试会不会掩盖 bug？** 只在「服务端明确返回错误文案」时重试，且默认只重试一次；纯超时不重试；重试用尽仍失败会抛带文案的异常。
6. **参数为空怎么处理？** 空字符串表示不输入，`input_text` 会 `clear()` 后输入空串；`None` 不是业务输入，不传。
7. **多个用例的登录态怎么隔离？** function 级 driver，每条用例重新启动浏览器、重新登录；Cookie 不共享。
8. **为什么密码不进日志？** `input_text` 只记录 locator，不记录 text；`login` 只记录用户名。
9. **位置参数会不会写错？** `login(username, password)` 语义明确，风险低；`fill_info(first, last, zip)` 三个都是 str，风险高，建议关键字传。
10. **如果新增一个账号要改代码吗？** 不用，YAML 加一组 `accounts.xxx`，用例用新 key 读取即可。

## 模块二：商品列表与详情（INV / DTL）

### 2.1 业务链路

```
登录成功 → 商品列表页 /inventory.html
  → 读取 6 个商品的名称/价格/图片
```

### 2.2 直白版

```python
def test_inventory(driver):

    names = [e.text for e in driver.find_elements(By.CSS_SELECTOR, ".inventory_item_name")]
```

问题：

### 2.4 动态定位器：slug

```python
@staticmethod
def add_button(slug: str) -> tuple:
    # 【入参】slug：str，商品短标识
    # 【出参】tuple：(By.CSS_SELECTOR, "[data-test='add-to-cart-{slug}']")
    return (By.CSS_SELECTOR, f"[data-test='add-to-cart-{slug}']")
```

调用链：

```python
backpack = get_product(4)                       # dict
slug = backpack["slug"]                         # "sauce-labs-backpack"
inventory_page.add_to_cart(slug)                # 传 str
  → self.click_robust(
        self.add_button(slug),                  # 此时才拼成 tuple
        lambda: self.is_element_visible(self.remove_button(slug), timeout=0),

```

**为什么定位器不写死？**

商品有 6 个，每个加购按钮的 `data-test` 都不同。用 `slug` 参数拼定位器，一份代码处理所有商品；新增商品只要 YAML 加数据。

### 2.5 加购：`click_robust` 的完整参数

```python
def add_to_cart(self, slug: str, retries: int = 1) -> None:
    # 【入参】slug：str；retries：int，默认 1
    # 【出参】None；成功时 Remove 按钮可见、角标 +1
    def _refresh_and_recheck() -> bool:
        # 【入参】无（闭包捕获 slug）
        # 【出参】bool：刷新后 Remove 是否可见
        logger.warning("加购[%s]仍未生效，刷新页面重渲染后复核", slug)
        self.refresh()
        self.wait_inventory_loaded()
        return self.is_element_visible(self.remove_button(slug), timeout=3)

    self.click_robust(
        self.add_button(slug),                          # locator
        lambda: self.is_element_visible(
            self.remove_button(slug), timeout=0),       # success 回调
        timeout=self.ADD_CONFIRM_TIMEOUT,               # 10s
        js_timeout=5,                                   # JS 点击后 5s
        retries=retries,                                # 重试次数
        post_js_recheck=_refresh_and_recheck,           # 刷新复核
        retry_allowed=lambda: not self.is_add_button_absent(slug),
        on_final_failure=lambda: self._attach_add_diagnostics(slug),
        fail_message=f"加购[{slug}]失败：原生点击/JS 点击/刷新复核均未生效",
    )
```

**参数逐项解释**：

| 参数 | 类型 | 来源 | 作用 |
| --- | --- | --- | --- |
| `self.add_button(slug)` | tuple | slug 动态拼 | 要点的按钮 |
| `success` | `Callable[[], bool]` | lambda 闭包 | Remove 可见 = 加购生效 |
| `timeout` | int | 类常量 `ADD_CONFIRM_TIMEOUT=10` | 原生点击后等多久 |
| `js_timeout` | int | 字面量 5 | JS 点击后等多久 |
| `retries` | int | 方法入参，默认 1 | 重试次数 |
| `post_js_recheck` | 函数 | 内嵌函数 | JS 点击仍无效时刷新复核 |
| `retry_allowed` | 回调 | lambda | 加购按钮还在才重试 |
| `on_final_failure` | 回调 | lambda | 采集诊断并返回 None → 抛最终异常 |
| `fail_message` | str | f-string | 失败信息带 slug |

**注意**：`on_final_failure` 返回 `None`（`_attach_add_diagnostics` 没有返回值），所以 `click_robust` 不会认为「已接管」，会继续抛 `TimeoutException`。如果希望它接管，回调必须返回 `True`（如 `open_cart` 的 `_url_fallback`）。

### 2.6 排序：数据驱动的三层键

YAML：

```yaml
sort_cases:
  - {case_id: "SAUCE-INV-003", value: "az", name: "名称升序(A→Z)", names_key: "az_names", prices_key: "az_prices"}

sort_expected:
  az_names: [...]
  az_prices: ["$29.99", ...]
```

用例：

```python
@pytest.mark.parametrize("case_data", CONFIG["sort_cases"],
                         ids=[case["case_id"] for case in CONFIG["sort_cases"]])
def test_product_sort(self, inventory_page, case_data):
    # 【入参】case_data：dict，含 value/names_key/prices_key
    expected_names = _expected_names(case_data)
    #   └─ CONFIG["sort_expected"][case_data["names_key"]]

    inventory_page.sort_and_wait_names(case_data["value"], expected_names)
    #                                ^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^
    #                                下拉框 value        期望名称序列
    assert inventory_page.get_sort_value() == case_data["value"]
    assert inventory_page.get_product_names() == expected_names
    assert inventory_page.get_price_numbers() == _expected_price_numbers(case_data)
```

**为什么用 `names_key` 而不是直接把期望列表写进 `sort_cases`？**

- 避免同一份期望数据重复；
- `sort_expected` 集中维护，`sort_cases` 只描述「用哪组期望」；
- 这是「数据引用数据」的间接层。

**`sort_and_wait_names` 的参数**：

```python
def sort_and_wait_names(self, value: str, expected_names: list,
                        timeout: Optional[int] = None) -> None:
    # 【入参】value：az/za/lohi/hilo
    # 【入参】expected_names：list[str]，来自 sort_expected.*_names
    # 【入参】timeout：可选；不传用 self.timeout
    # 【出参】None；等待 DOM 顺序变为期望序列
    self.sort_by(value)
    base_timeout = timeout or self.timeout     # 注意：0 会被吞掉
    self.wait_until(
        lambda _: self.get_product_names() == expected_names,
        timeout=base_timeout,
        fail_message=f"排序 {value} 未在超时内生效",
    )
```

**特殊账号的两种排序等待**：

- `sort_and_wait_settle(value, base_names, timeout=3)`：等顺序变化，等不到也继续（problem_user 排序失效）；
- `sort_and_tolerate_alert(value)`：排序后若有原生 alert，自动接受（error_user 会弹 `Sorting is broken!`）。

### 2.7 详情页跳转：`_enter_detail(product_id)`

```python
def _enter_detail(self, inventory_page, page_factory, product_id):
    # 【入参】inventory_page：已登录的 InventoryPage
    # 【入参】page_factory：页面工厂函数
    # 【入参】product_id：int，来源 backpack["id"]
    # 【出参】ItemPage 实例
    inventory_page.click_product_link(product_id)
    inventory_page.wait_url_contains(f"/inventory-item.html?id={product_id}")
    #                                           ^^^^^^^^^^^^^^^^^^^ 用 id 拼期望 URL 片段
    item_page = page_factory(ItemPage)
    item_page.wait_detail_loaded()
    return item_page
```

**数据流**：

```
backpack = get_product(4) → id=4
  → click_product_link(4)
      → product_title_link(4) → (By.CSS_SELECTOR, "a[data-test='item-4-title-link']")
      → click_robust(...)
  → wait_url_contains("/inventory-item.html?id=4")
  → page_factory(ItemPage) → ItemPage(driver, timeout=10, poll_frequency=0.5)
  → wait_detail_loaded()
  → return ItemPage
```

### 2.10 【面试必背话术】

> 商品模块的核心是「数据驱动 + 动态定位」。商品数据在 YAML 里是 slug/id/name/price 四元组，`get_product(4)` 拿到 dict，再用 slug 拼加购按钮的 `data-test`，这样一份代码覆盖 6 个商品。排序用 parametrize 跑 4 组，每组数据只描述「用哪个排序值、引用哪组期望名称/价格」，期望序列放在 `sort_expected` 里集中维护。加购不是简单 `click`，而是 `click_robust`：传入「Remove 可见」作为成功条件，原生点击没生效就 JS 点击，再不行刷新复核，最后重试；失败会采集按钮坐标、命中的元素、localStorage 购物车状态，附件进报告。详情页按钮的 `data-test` 是通用值，不带 slug，所以详情页的加购方法不需要 slug 参数——方法签名是跟着实际 DOM 走的。

### 2.11 【面试官高频追问清单】

1. **slug 从哪来？** YAML 商品表 → `get_product(id)` → dict → `["slug"]`。
2. **为什么不用 XPath 拼？** 优先 `data-test`，稳定；CSS 选择器可读性好；XPath 在结构变化时脆。
3. **`add_to_cart` 的 `success` 为什么是 lambda？** 成功条件依赖 slug 和页面状态，BasePage 不知道业务，必须由页面层注入。
4. **加购失败怎么定位？** 诊断附件含按钮坐标、`elementFromPoint` 命中元素、`localStorage` 购物车内容、加购/移除按钮清单。
5. **排序期望值为什么用 `names_key` 间接引用？** 避免重复数据，集中维护；一组排序数据只描述「引用哪组期望」。
6. **`sort_and_wait_names` 的 timeout 默认值有什么坑？** 用了 `timeout or self.timeout`，传 `0` 会回退；`_wait` 里已经用 `is None` 修正，这里是一处不一致。
7. **多件商品为什么逐件等角标？** 每加一件断言角标 = index，能定位是哪一件没加上；批量加完再断言总数，失败信息不够精确。
8. **详情页为什么不用 slug？** 实测详情页按钮 `data-test` 是 `add-to-cart`，通用值；方法签名跟着 DOM 走。
9. **图片断言为什么先等 naturalWidth？** 图片解码有延迟，直接读会得到 0 的误报；`wait_all_images_loaded` 先等全部 `naturalWidth>0`。
10. **problem_user 图片异常怎么断言？** 不写死具体图片，断言「6 个 src 的唯一数 = 1」，这是与标准基线「6 个不同 src」的差异。

### 3.3 项目版：模块级前置 `_prepare_cart`

```python
def _prepare_cart(inventory_page, page_factory):
    # 【入参】inventory_page：fixture，已登录的列表页
    # 【入参】page_factory：fixture，页面工厂
    # 【出参】CartPage：已加载、含 2 件商品的购物车页
    with allure.step("前置业务流程：加购默认商品并逐件断言购物车角标"):

            # 【参数】index 从 1 开始；slug 来自 YAML list
            inventory_page.add_to_cart(slug)
            inventory_page.wait_badge_text(str(index))     # 等角标 = index

    with allure.step("前置业务流程：进入购物车页面"):
        inventory_page.open_cart(fallback_url=CONFIG["urls"]["cart"])
        cart_page = page_factory(CartPage)
        cart_page.wait_cart_page_loaded()
    with allure.step("前置业务流程：校验删除按钮已就位"):
        try:
            for slug in CONFIG["checkout"]["default_item_slugs"]:
                cart_page.find_element(cart_page.remove_button(slug), timeout=10)
        except TimeoutException:
            cart_page.refresh()
            cart_page.wait_cart_page_loaded()
            for slug in CONFIG["checkout"]["default_item_slugs"]:
                cart_page.find_element(cart_page.remove_button(slug), timeout=10)
    return cart_page
```

**参数逐项**：

| 参数/变量 | 类型 | 来源 | 作用 |
| --- | --- | --- | --- |
| `inventory_page` | `InventoryPage` | fixture | 已登录列表页 |
| `page_factory` | 函数 | fixture | 创建 `CartPage` |
| `default_item_slugs` | `list[str]` | YAML | 默认两件商品 |
| `index` | int | `enumerate(start=1)` | 期望角标值 |
| `slug` | str | 循环变量 | 加购和删除按钮定位 |

**为什么不用 `cart_page` fixture？**

项目里确实有 `cart_page` fixture，但 `test_cart` / `test_checkout` 选择自己的 `_prepare_cart`，因为：

- 它要在加购过程中**逐件断言角标**，失败时能指出是哪件商品没加上；
- 它要校验购物车页的删除按钮已就位，必要时刷新；
- fixture 更适合「稳定前置」，模块函数更适合「带业务断言的准备」。

### 3.4 购物车页删除：`remove_item(slug)`

```python
def remove_item(self, slug: str) -> None:
    # 【入参】slug：str，要删除的商品
    # 【出参】None；成功时该商品行消失、角标减少
    def _refresh_and_recheck() -> bool:
        # 【入参】无（闭包捕获 slug）
        # 【出参】bool：刷新后移除按钮是否消失
        self.refresh()
        self.wait_cart_page_loaded()
        return not self.is_element_visible(self.remove_button(slug), timeout=5)

    self.click_robust(
        self.remove_button(slug),
        lambda: not self.is_element_visible(self.remove_button(slug), timeout=0),
        timeout=10,
        js_timeout=5,
        retries=0,                 # 删除是幂等动作，单轮执行，不重复点击
        post_js_recheck=_refresh_and_recheck,
        fail_message=f"删除购物车商品[{slug}]失败",
    )
```

**为什么 `retries=0`？**

删除可能已经被执行（只是 UI 未刷新），重复点击可能删掉其他商品或触发异常；单轮 + 刷新复核更安全。

### 3.5 `CartPage.remove_button` 的 staticmethod 坑

```python
class CartPage(BasePage):
    remove_button = staticmethod(InventoryPage.remove_button)
```

**如果不加 `staticmethod`**：

```
InventoryPage.remove_button          → 普通函数 function(slug)
CartPage.remove_button               → 赋给类后成为方法
cart_page.remove_button(slug)        → 实际调用 remove_button(self, slug) → 参数数量错
```

这是「函数描述符绑定」：函数放在类属性上会自动绑定为实例方法。`staticmethod` 告诉 Python「不要绑定」。

### 3.6 用例：删除联动

```python
def test_remove_item_from_cart_page(self, inventory_page, page_factory):
    cart_page = _prepare_cart(inventory_page, page_factory)
    backpack = get_product(4)
    bike_light = get_product(0)

    cart_page.remove_item(backpack["slug"])
    assert cart_page.get_cart_item_count() == 1
    assert cart_page.get_cart_item_names() == [bike_light["name"]]
    assert cart_page.get_badge_text() == "1"

    assert cart_page.is_badge_absent()
```

**数据链**：

```

get_product(0) → dict → ["name"] → 期望剩余商品名
get_cart_item_count() → int → 与 1/0 比较
get_badge_text() → str → 与 "1" 比较
is_badge_absent() → bool → 断言角标从 DOM 移除
```

**为什么角标消失要用 `is_badge_absent` 而不是 `get_badge_text() == "0"`？**

站点在角标为 0 时会把元素从 DOM 移除，`get_badge_text()` 会超时；`is_badge_absent()` 判断元素不存在，才符合实际行为。

5. **`remove_item` 为什么 `retries=0`？** 删除幂等，重复点击有副作用；单轮 + 刷新复核。
6. **`CartPage.remove_button` 为什么 staticmethod？** 直接赋值会把函数绑定成方法，多传 self。

9. **购物车预置 2 件商品，数据从哪来？** YAML `checkout.default_item_slugs`。
10. **如果商品没加上，后续断言会怎样？** `_prepare_cart` 里逐件断言角标，提前失败，避免「购物车数量不对」的误导性失败。

### 4.4 点击 Continue 的成功条件：两种结果

```python
def click_continue(self) -> None:
    # 【入参】无
    # 【出参】None
    self.click_until(self.CONTINUE, self._is_continue_applied,
                     fail_message="点击 Continue 后既未进入概览页，也未出现校验提示")

def _is_continue_applied(self) -> bool:
    # 【入参】无
    # 【出参】bool：Finish 可见（成功进入概览）或错误提示可见（校验拦截）
    return (self.is_element_visible(self.FINISH, timeout=0)
```

```python
    return {
```

### 4.11 【面试官高频追问清单】

7. **超长串长度从哪来？** YAML `checkout.long_input_length=300`。

### 5.3 项目版：打开菜单

```python
def open_menu(self, timeout: Optional[int] = None) -> None:
    # 【入参】timeout：Optional[int]；None → 用 MENU_TIMEOUT=20
    # 【出参】None；成功时 aria-hidden=false 且关键元素可见
    self.click(self.BURGER_BTN)
    wait_time = timeout or self.MENU_TIMEOUT
    try:
        self.wait_attribute_equals(self.MENU_WRAP, "aria-hidden", "false", min(wait_time, 10))
    except TimeoutException:
        # CI 无头 Chrome 偶发点击丢失：JS 再点一次
        self.js_click(self.BURGER_BTN)
        self.wait_attribute_equals(self.MENU_WRAP, "aria-hidden", "false", wait_time)
    self.wait_until(
        lambda _: (self.is_element_visible(self.CROSS_BTN, timeout=0)
                   and all(self.is_element_visible(locator, timeout=0)
                           for locator in (self.ALL_ITEMS, self.ABOUT, self.RESET, self.LOGOUT))),
        timeout=wait_time,
        fail_message="侧边栏展开后关键要素未全部可见",
    )
```

**为什么用 `aria-hidden` 作为权威状态？**

菜单收起是 CSS `transform` 移出画布，Selenium 的 `is_displayed()` 仍可能返回 True；`aria-hidden` 是站点明确暴露的开合状态。

### 5.5 Logout：回调参数大全

```python
def click_logout(self, retries: int = 1, fallback_url: Optional[str] = None) -> None:
    # 【入参】retries：重试次数；fallback_url：兜底登录页地址
    # 【出参】None
    def _reopen_menu_if_closed() -> None:
        if self.is_menu_closed():
            self.open_menu()

    def _cookie_fallback() -> bool:
        # 【出参】bool：True=已接管（清 Cookie + 直达登录页）
        if not fallback_url:
            return False
        self.delete_all_cookies()
        self.open_url(fallback_url)
        self.find_element(LoginPage.USERNAME_INPUT)
        return True

    self.click_robust(
        self.LOGOUT,
        lambda: self.is_element_visible(LoginPage.USERNAME_INPUT, timeout=0),  # 成功条件
        timeout=self.timeout,
        js_timeout=5,
        retries=retries,
        retry_allowed=lambda: self.get_element_count_immediate(self.MENU_WRAP) > 0,
        before_retry=_reopen_menu_if_closed,
        on_final_failure=_cookie_fallback,
        fail_message="点击 Logout 后未跳转回登录页",
    )
```

**参数难点**：

- `LoginPage.USERNAME_INPUT` 是跨页面引用：MenuPage 复用 LoginPage 的定位器，作为「已回到登录页」的权威标志；
- `_reopen_menu_if_closed`：第一次点击后菜单可能自动收起，重试前要重新展开；
- `_cookie_fallback` 返回 `True` 表示「我已经接管成功」，`click_robust` 不再抛异常；
- `fallback_url` 不传时，兜底直接返回 False，保留原始异常。

| `open_menu(timeout)` | 可选超时 | 默认 20 | `None` | 副作用 |
| `close_menu(timeout)` | 可选超时 | 默认 20 | `None` | 副作用 |

### 5.7 【面试必背话术】

> 菜单模块的难点是「状态不可靠」：菜单是滑动动画，`is_displayed` 不能准确判断开合，所以用 `aria-hidden` 作为权威状态；点击后既等属性翻转，又等菜单项真正可见。About 外链要兼容新旧两种实现：新窗口用窗口数判断，同窗口用 URL 前缀判断，所以方法返回 bool，调用方根据返回值决定关闭窗口还是后退。Logout 的成功条件是「登录页输入框可见」，不是简单的 URL 判断；重试前如果菜单自动收起会重新展开，最终兜底是清 Cookie + URL 直达。

### 5.8 【面试官高频追问清单】

1. **为什么不用 `is_displayed` 判断菜单开合？** CSS transform 移出画布，Selenium 仍可能判定可见；`aria-hidden` 是站点权威状态。
2. **`open_about_and_navigate` 为什么返回 bool？** 站点可能新窗口或同窗口，调用方要按不同方式清理。
3. **`timeout` 为什么默认 20 而不是 10？** 菜单滑动动画在 CI/低负载机器可能超过 10s；`MENU_TIMEOUT=20` 与默认解耦。
4. **`click_logout` 的 `before_retry` 做什么？** 首次点击后菜单可能自动收起，重试前重新展开。
5. **`on_final_failure` 返回 True 什么意思？** 页面层已接管（清 Cookie + 直达登录页），基础层不再抛异常。
6. **为什么 Logout 成功条件是输入框可见？** URL 可能已经变但页面还没渲染；元素可见才是「真正回到登录页」。
7. **Reset 后为什么要刷新？** 站点版本差异：清购物车后按钮状态可能不重渲染；先原地等 5s，不行刷新再等。
8. **菜单项定位为什么用 `data-test`？** 比 class 稳定，站点升级 class 可能变。
9. **`fallback_url` 从哪来？** 用例传 `CONFIG["base_url"]`；页面层不读配置。
10. **窗口切换的参数是什么？** `switch_to_new_window()` 无参，内部取 `window_handles[-1]`；`switch_to_window(index)` 按索引。

### 6.2 特殊账号：同一用例内多次登录

```python
def _login_as(login_page, page_factory, account_key: str):
```

2. **基线数据跨用例共享吗？** 不共享，在同一条用例内采集，避免环境差异和顺序依赖。
3. **glitch 为什么用相对基线？** 机器性能不同，绝对阈值会误报；相对基线衡量「比正常慢多少」。
4. **软断言怎么做？** 数值写 Allure 附件；配置开关打开才 `assert`。
5. **error_user 为什么不写死失败商品？** 站点版本可能变，写死会误报；断言「成功数 < 6」这种结构性差异。
6. **problem_user 图片怎么断言？** 6 个 src 的唯一数 = 1，与标准基线「6 个不同」对比。
7. **排序失效怎么等？** `sort_and_wait_settle` 等 3s，没变化就按当前 DOM 断言，不直接失败。
8. **原生 alert 怎么处理？** `sort_and_tolerate_alert` 检测到 alert 就 accept，避免污染后续 WebDriver 命令。
9. **account_key 参数为什么用字符串？** 作为 YAML `accounts` 的键，易读、可配置；传错会 `KeyError`，属于配置错误。
10. **偏移阈值从哪来？** YAML `special_users.visual_offset.x/y`，代码不写死。

### 7.2 项目版关键代码

```python
def test_full_order_flow_smoke(self, inventory_page, page_factory):

    inventory_page.add_items_to_cart(DEFAULT_SLUGS)
    for product in expected_products:
        assert inventory_page.get_button_text(
            inventory_page.remove_button(product["slug"])) == E2E["remove_button_text"]
    assert inventory_page.get_badge_text() == str(len(expected_products))

    # 节点3：购物车
    inventory_page.open_cart(fallback_url=URLS["cart"])
    cart = page_factory(CartPage)
    cart.wait_cart_page_loaded()
    assert cart.get_cart_item_names() == [p["name"] for p in expected_products]
    assert cart.get_cart_item_prices() == [f"${p['price']}" for p in expected_products]

    # 节点4：结算表单
    cart.click_checkout()
    checkout = page_factory(CheckoutPage)
    checkout.wait_step_one_loaded()
    checkout.fill_info_and_continue(
        valid_info["first"], valid_info["last"], valid_info["zip"])
    checkout.wait_overview_loaded()

    # 节点5：金额
    amounts = checkout.get_summary_amounts()
    subtotal = Decimal(backpack["price"]) + Decimal(bike_light["price"])
    tax = (subtotal * Decimal("0.08")).quantize(Decimal("0.01"), ROUND_HALF_UP)
    assert amounts["subtotal"] == subtotal
    assert amounts["tax"] == tax
    assert amounts["total"] == subtotal + tax

    # 节点6：完成
    checkout.click_finish()
    checkout.wait_complete_loaded()
    assert checkout.get_complete_header() == CONFIG["checkout"]["complete_header"]
    assert checkout.is_badge_absent()
```

**参数链**：

```
expected_products = [get_product(4), get_product(0)]   # list[dict]
  → p["slug"] → remove_button(slug) → 断言按钮文案
  → p["name"] → 购物车名称断言
  → p["price"] → f"${price}" 价格断言
  → Decimal(price) → 金额计算
DEFAULT_SLUGS = CONFIG["checkout"]["default_item_slugs"] → add_items_to_cart
valid_info = CONFIG["checkout"]["valid_info"] → fill_info_and_continue
```

**节点间数据传递**：

- 加购的 slug 和购物车断言的名称/价格都来自同一份 `expected_products`，保证「加的是什么、断言的就是什么」；
- 结算金额用商品价格重新计算，和页面显示值比较；
- 完成页断言角标消失，验证链路终态。

### 7.4 【面试必背话术】

> E2E 用例的价值是「一条用例从登录走到完成页」，任何一个节点失败都能定位链路断点。它和节点级用例的分工是：节点级各管一段、靠 fixture 到达现场；E2E 在一个会话里串起来，节点间的数据一致性靠断言保证，而不是靠 fixture 重建。比如加购用的商品列表 `expected_products`，后面购物车的名称/价格、结算的金额计算都复用它，保证「加的是什么就断言什么」。这条用例也是 smoke 标记，CI 冒烟会跑。

### 7.5 【面试官高频追问清单】

1. **E2E 和节点级用例重复吗？** 不重复：节点级定位具体功能，E2E 验证链路连贯和数据一致性。
2. **E2E 的数据怎么传递？** 同一条用例内用局部变量和页面对象，不跨用例。
3. **E2E 失败怎么定位？** 每个节点都有 `allure.step`，报告里能看到卡在哪个节点。
4. **为什么 E2E 不用 `cart_page` fixture？** 它要自己控制链路顺序和节点断言，fixture 会隐藏过程。
5. **金额为什么重新算？** 用商品价格重算 subtotal/tax/total，和页面显示比较，验证计算逻辑，而不是只比字符串。
6. **`expected_products` 为什么不用 fixture？** 局部变量生命周期清晰，避免隐式共享。

## 8. 七个模块的共性总结

| 共性 | 体现 |
| --- | --- |
| 数据外置 | 账号、URL、期望值、商品、参数化数据全在 YAML |
| 动态定位 | slug/id 拼 `data-test`；详情页通用按钮 |
| 动作 + 成功条件 | `click_robust/click_until` 用回调定义「成功」 |
| 显式等待 | 所有断言前先等状态收敛 |
| 数据链 | 上一步返回值作为下一步入参；类型逐层变化 |
| 分层收窄 | 用例只传业务参数，页面层拼定位器，基础层只收 locator/text/timeout |
| 失败取证 | 截图、GIF、控制台日志、页面源码、诊断 JSON |
| 参数隔离 | function driver + 深拷贝 + 独立 parametrize |
